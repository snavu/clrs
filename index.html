Getting Started

We begin with the most concrete object in the book: a small, specific algorithm, and the tools to say exactly what "efficient" means for it. The two algorithms in this chapter — insertion sort and merge sort — serve as the bedrock upon which all subsequent analysis rests. Master these and you have the vocabulary to attack everything that follows.

2.1Insertion Sort

Insertion sort is the algorithm most people would invent if handed a pile of index cards to sort. You pick up one card at a time, and slide each new card into its correct position among the cards you have already sorted. Formally:

The Sorting Problem Input. A sequence of $n$ numbers $\langle a_1, a_2, \ldots, a_n \rangle$.
Output. A permutation $\langle a'_1, a'_2, \ldots, a'_n \rangle$ of the input such that $a'_1 \leq a'_2 \leq \cdots \leq a'_n$.

The Algorithm

We present insertion sort in the CLRS pseudocode style. The variable $j$ marks the "current" card being inserted; indices $1$ through $j-1$ are already in sorted order; $i$ scans backward through that sorted prefix looking for the correct insertion point.

Insertion-Sort(A)
for j = 2 to A.length    key = A[j]    // Insert A[j] into the sorted sequence A[1..j-1].    i = j - 1    while i > 0 and A[i] > key        A[i + 1] = A[i]        i = i - 1    A[i + 1] = key

Best and Worst Case Analysis

Let $t_j$ denote the number of times the while-loop test on line 5 is executed for a given value of $j$. We count the cost of each line as a constant $c_k$ multiplied by the number of times that line executes:

LineCostTimes
1   for j = 2 to n$c_1$$n$
2   key = A[j]$c_2$$n-1$
4   i = j - 1$c_4$$n-1$
5   while ...$c_5$$\sum_{j=2}^{n} t_j$
6   A[i+1] = A[i]$c_6$$\sum_{j=2}^{n}(t_j - 1)$
7   i = i - 1$c_7$$\sum_{j=2}^{n}(t_j - 1)$
8   A[i+1] = key$c_8$$n-1$

The total running time $T(n)$ is the sum of these products. We analyse two extremes.

Best Case — input already sorted

If $A$ is already in ascending order, then for each $j$ the test A[i] > key on line 5 is false on the first evaluation. Hence $t_j = 1$ for all $j = 2, \ldots, n$.

$$T(n) = c_1 n + (c_2 + c_4 + c_5 + c_8)(n-1) = an + b$$

for constants $a, b$. This is a linear function of $n$, so the best-case running time is $\Theta(n)$.

Worst Case — input in reverse sorted order

If $A$ is in strictly decreasing order, each key $A[j]$ must be compared with every element $A[1], \ldots, A[j-1]$; the inner loop runs until $i = 0$. Hence $t_j = j$, giving

$$\sum_{j=2}^{n} t_j = \sum_{j=2}^{n} j = \frac{n(n+1)}{2} - 1, \qquad \sum_{j=2}^{n}(t_j - 1) = \frac{n(n-1)}{2}.$$

Substituting and collecting constants gives

$$T(n) = \left(\tfrac{c_5}{2} + \tfrac{c_6}{2} + \tfrac{c_7}{2}\right)n^2 + \left(c_1 + c_2 + c_4 + \tfrac{c_5}{2} - \tfrac{c_6}{2} - \tfrac{c_7}{2} + c_8\right)n - (c_2 + c_4 + c_5 + c_8).$$

This is a quadratic function of $n$, so the worst-case running time is $\Theta(n^2)$.

The average-case running time is also $\Theta(n^2)$: on average half the sorted prefix must be scanned before the correct insertion point is found, giving $t_j \approx j/2$, and the leading term is still quadratic.

Loop Invariant — Proof of Correctness

A loop invariant is an assertion about the state of a computation that holds at designated points during the execution of a loop. We use it to prove correctness the same way mathematical induction proves statements about the natural numbers: we must establish three properties.

Loop Invariant Proof Method Initialization. The invariant is true prior to the first iteration of the loop.
Maintenance. If the invariant is true before an iteration, it remains true before the next iteration.
Termination. When the loop terminates, the invariant (combined with the reason the loop terminated) yields a useful property that helps show the algorithm is correct.
Theorem 2.1 (Correctness of Insertion-Sort) Invariant: At the start of each iteration of the for-loop on line 1 (with loop index $j$), the subarray $A[1\mathinner{.\,.}j-1]$ consists of the elements originally in $A[1\mathinner{.\,.}j-1]$, but in sorted order.

We verify the three conditions.

Initialization. Before the first iteration, $j = 2$, so $A[1\mathinner{.\,.}j-1] = A[1\mathinner{.\,.}1]$, which is a single-element subarray. It is trivially sorted and trivially a permutation of itself. The invariant holds. (That the base case is $j=2$ and not $j=1$ is a common confusion — the invariant is stated at the start of an iteration, and the first iteration starts with $j=2$.)

Maintenance. Assume the invariant holds at the start of iteration $j$: that is, $A[1\mathinner{.\,.}j-1]$ is a sorted permutation of the original $A[1\mathinner{.\,.}j-1]$. We must show it holds at the start of iteration $j+1$, i.e. that $A[1\mathinner{.\,.}j]$ is a sorted permutation of the original $A[1\mathinner{.\,.}j]$.

The body of the iteration saves $\textit{key} = A[j]$ and then repeatedly shifts elements of $A[1\mathinner{.\,.}j-1]$ one position to the right — replacing $A[i+1]$ with $A[i]$ — for as long as $A[i] > \textit{key}$ and $i > 0$. (A formal proof at this level requires its own inner invariant for the while-loop; informally: after each inner iteration, $A[i+2\mathinner{.\,.}j]$ is a rightward shift of the original $A[i+1\mathinner{.\,.}j-1]$, and every element in that range exceeds $\textit{key}$.) The loop terminates when either $i = 0$ or $A[i] \leq \textit{key}$; in either case, the assignment $A[i+1] = \textit{key}$ places $\textit{key}$ immediately to the right of an element that does not exceed it (or at position $1$). Thus $A[1\mathinner{.\,.}j]$ is sorted and is a permutation of the original $A[1\mathinner{.\,.}j]$.

Termination. The loop terminates when $j$ exceeds $n$, i.e. when $j = n+1$. Substituting into the invariant, the subarray $A[1\mathinner{.\,.}n]$ consists of the elements originally in $A[1\mathinner{.\,.}n]$, in sorted order. But $A[1\mathinner{.\,.}n]$ is the entire array, so the algorithm has correctly sorted $A$.■

2.2Analyzing Algorithms

To analyze an algorithm is to predict the resources it will require. Usually we care about time, but memory, bandwidth, or energy may be equally relevant. Before any analysis is possible we must commit to a model of computation; CLRS fixes the Random-Access Machine (RAM).

The RAM Model

Instructions execute one after another, with no concurrency. Each instruction takes a constant amount of time. The primitive instructions include arithmetic (add, subtract, multiply, divide, remainder, floor, ceiling), data movement (load, store, copy), and control (conditional and unconditional branch, subroutine call and return). Data types are integer and floating-point, with a word size that grows only modestly — specifically, with $c \log n$ bits for some constant $c \geq 1$ on inputs of size $n$.

Input Size and Running Time

Two quantities need precise definition.

Input size. The natural measure depends on the problem. For sorting, it is the number of items $n$. For integer multiplication, it is the total number of bits in the input. For a graph algorithm, it is often a pair $(|V|, |E|)$.

Running time. On a given input, the running time is the number of primitive operations (or "steps") executed. We follow the convention that each line of pseudocode takes constant time, though the constants may differ from line to line. This makes our analysis machine-independent up to a constant factor — exactly the granularity $\Theta$-notation (developed in Chapter 3) is designed for.

Worst Case, Best Case, Average Case

For a fixed algorithm, the running time depends on the input. We distinguish:

  • Worst-case running time $T(n)$: the maximum running time over all inputs of size $n$. This is the default. It gives an upper bound for any input, it occurs often in practice, and the "average case" is frequently as bad as the worst.
  • Best-case running time: the minimum over inputs of size $n$. Typically too optimistic to be useful on its own.
  • Average-case running time: the expectation over inputs of size $n$, under some distribution — commonly the uniform distribution. Requires probabilistic analysis and a justified distribution.

Order of Growth

Even the exact expression for $T(n)$ depends on machine-specific constants. For comparing algorithms, only the rate of growth matters as $n \to \infty$. For insertion sort we summarize:

Summary — Insertion Sort

$$T_{\text{best}}(n) = \Theta(n), \qquad T_{\text{worst}}(n) = \Theta(n^2), \qquad T_{\text{avg}}(n) = \Theta(n^2).$$

2.3Designing Algorithms

Insertion sort uses an incremental design: we build up the sorted prefix one element at a time. In this section we introduce a different paradigm that will reappear throughout the book.

2.3.1 The Divide-and-Conquer Approach

Divide-and-Conquer Divide the problem into a number of subproblems that are smaller instances of the same problem.
Conquer the subproblems by solving them recursively. If the subproblem size is small enough (the base case), solve it directly.
Combine the solutions to the subproblems into the solution for the original problem.

Merge Sort

Merge sort applies this paradigm to sorting. To sort $A[p\mathinner{.\,.}r]$:

  1. Divide: split the $n$-element subarray into two subarrays of $n/2$ elements each, namely $A[p\mathinner{.\,.}q]$ and $A[q+1\mathinner{.\,.}r]$ where $q = \lfloor (p+r)/2 \rfloor$.
  2. Conquer: sort each half recursively using merge sort.
  3. Combine: merge the two sorted halves into a single sorted array.

The recursion bottoms out when a subarray has just one element (which is trivially sorted). The key subroutine is MERGE, which assumes $A[p\mathinner{.\,.}q]$ and $A[q+1\mathinner{.\,.}r]$ are each already sorted.

Merge(A, p, q, r)
n_1 = q - p + 1n_2 = r - qlet L[1..n_1 + 1] and R[1..n_2 + 1] be new arraysfor i = 1 to n_1    L[i] = A[p + i - 1]for j = 1 to n_2    R[j] = A[q + j]L[n_1 + 1] = ∞R[n_2 + 1] = ∞i = 1j = 1for k = p to r    if L[i] <= R[j]        A[k] = L[i]        i = i + 1    else A[k] = R[j]        j = j + 1

The use of $\infty$ as a sentinel eliminates a tedious boundary check: neither $L$ nor $R$ can be exhausted before position $r$ because each contains a value ($\infty$) that is never less than the other.

Merge-Sort(A, p, r)
if p < r    q = ⌊(p + r) / 2⌋    Merge-Sort(A, p, q)    Merge-Sort(A, q + 1, r)    Merge(A, p, q, r)

Correctness of MERGE

Theorem 2.2 (Correctness of Merge) Invariant: At the start of each iteration of the for-loop on line 12, the subarray $A[p\mathinner{.\,.}k-1]$ contains the $k - p$ smallest elements of $L[1\mathinner{.\,.}n_1+1]$ and $R[1\mathinner{.\,.}n_2+1]$, in sorted order. Moreover, $L[i]$ and $R[j]$ are the smallest elements of their arrays that have not yet been copied back into $A$.

Initialization. Before the first iteration, $k = p$, so $A[p\mathinner{.\,.}k-1] = A[p\mathinner{.\,.}p-1]$ is empty; it contains the $0$ smallest elements trivially. Since $i = j = 1$, $L[i]$ and $R[j]$ are the first (smallest) elements of their respective sorted arrays.

Maintenance. Suppose $L[i] \leq R[j]$; then $L[i]$ is the smallest element not yet copied back. The body copies $L[i]$ to $A[k]$ and increments both $i$ and $k$; the invariant holds for the new values. The case $L[i] > R[j]$ is symmetric.

Termination. The loop terminates when $k = r+1$. The invariant then says $A[p\mathinner{.\,.}r]$ contains the $r - p + 1 = n_1 + n_2$ smallest elements of $L$ and $R$ in sorted order. The only elements not among these are the two sentinels $\infty$. Hence $A[p\mathinner{.\,.}r]$ is exactly the sorted union of the original $L[1\mathinner{.\,.}n_1]$ and $R[1\mathinner{.\,.}n_2]$.■

2.3.2 Analyzing Divide-and-Conquer Algorithms

The running time of a divide-and-conquer algorithm is naturally described by a recurrence. Let $T(n)$ be the running time on a problem of size $n$. If the problem is small enough (size $\leq c$ for some constant $c$), the direct solution takes constant time $\Theta(1)$. Otherwise:

  • The divide step takes $D(n)$ time.
  • We solve $a$ subproblems, each of size $n/b$, in total time $a \cdot T(n/b)$.
  • The combine step takes $C(n)$ time.

This gives the general recurrence

$$T(n) = \begin{cases} \Theta(1) & \text{if } n \leq c, \\ aT(n/b) + D(n) + C(n) & \text{otherwise.} \end{cases}$$

The Merge-Sort Recurrence

For merge sort on $n$ elements with $n > 1$:

  • Divide: compute the midpoint $q$. This is $D(n) = \Theta(1)$.
  • Conquer: recursively sort two subproblems of size $n/2$, totalling $2T(n/2)$.
  • Combine: the MERGE procedure runs in $\Theta(n)$ on an $n$-element subarray (it is a single for-loop from $p$ to $r$ with constant-time body).

Therefore

$$T(n) = \begin{cases} \Theta(1) & \text{if } n = 1, \\ 2T(n/2) + \Theta(n) & \text{if } n > 1. \end{cases}$$

Theorem 2.3 (Merge-Sort Running Time) The recurrence above has solution $T(n) = \Theta(n \log n)$.

A rigorous derivation appears in §4.4 via the recursion-tree method and in §4.5 as Case 2 of the master theorem. The intuition, however, is easy to state now: the recursion tree for merge sort has depth $\log_2 n$, and each level performs $\Theta(n)$ work in total (the top level does $n$ work, the next level does $n/2 + n/2 = n$ work, and so on). Total work: $\Theta(n) \cdot \Theta(\log n) = \Theta(n \log n)$.

Q3. In the general divide-and-conquer recurrence $T(n) = aT(n/b) + D(n) + C(n)$, which parameter most directly controls the depth of the recursion tree?

  • $b$

Growth of Functions

Chapter 2 justified the convention that lines of pseudocode run in constant time — but only up to a constant. To compare algorithms meaningfully we need a vocabulary that ignores constant factors and low-order terms. That vocabulary is asymptotic notation.

3.1Asymptotic Notation

The symbols $O$, $\Theta$, $\Omega$, $o$, and $\omega$ describe the asymptotic running time of an algorithm — its behavior as $n \to \infty$. Each describes a set of functions; equations like "$T(n) = O(n^2)$" are abuses of notation that should be read as "$T(n)$ is an element of the set $O(n^2)$".

$\Theta$-Notation — Asymptotic Tight Bound

Definition 3.1 ($\Theta$)

For a given function $g(n)$, we denote by $\Theta(g(n))$ the set of functions $$\Theta(g(n)) = \{\, f(n) : \exists\, c_1, c_2 > 0,\ n_0 > 0\ \text{such that}\ 0 \leq c_1 g(n) \leq f(n) \leq c_2 g(n)\ \text{for all } n \geq n_0 \,\}.$$

Informally: $f(n)$ is squeezed between $c_1 g(n)$ and $c_2 g(n)$ for all sufficiently large $n$. Note the requirement $f(n) \geq 0$ — all functions we use with asymptotic notation are asymptotically nonnegative.

Example 3.1 — $\tfrac{1}{2}n^2 - 3n = \Theta(n^2)$

We must find constants $c_1, c_2, n_0 > 0$ such that $$c_1 n^2 \leq \tfrac{1}{2} n^2 - 3n \leq c_2 n^2 \quad \text{for all } n \geq n_0.$$

Dividing by $n^2$ (valid for $n > 0$): $c_1 \leq \tfrac{1}{2} - \tfrac{3}{n} \leq c_2$. The right inequality holds for all $n \geq 1$ with $c_2 = \tfrac{1}{2}$. The left inequality holds for all $n \geq 7$ with $c_1 = \tfrac{1}{14}$ (since then $\tfrac{1}{2} - \tfrac{3}{7} = \tfrac{1}{14}$). Choosing $n_0 = 7$, $c_1 = \tfrac{1}{14}$, $c_2 = \tfrac{1}{2}$ completes the proof.■

$O$-Notation — Asymptotic Upper Bound

Definition 3.2 ($O$) $$O(g(n)) = \{\, f(n) : \exists\, c > 0,\ n_0 > 0\ \text{such that}\ 0 \leq f(n) \leq c g(n)\ \text{for all } n \geq n_0 \,\}.$$

Big-$O$ gives an upper bound only, not necessarily tight. Note $\Theta(g(n)) \subseteq O(g(n))$.

The idiomatic use: "the running time of insertion sort is $O(n^2)$" — meaning no input causes more than a constant times $n^2$ steps. Because $O$ bounds the worst case from above, it is the workhorse of the field.

$\Omega$-Notation — Asymptotic Lower Bound

Definition 3.3 ($\Omega$) $$\Omega(g(n)) = \{\, f(n) : \exists\, c > 0,\ n_0 > 0\ \text{such that}\ 0 \leq c g(n) \leq f(n)\ \text{for all } n \geq n_0 \,\}.$$
Theorem 3.1 — The $\Theta$ / $O$ / $\Omega$ Connection For any two functions $f(n)$ and $g(n)$: $$f(n) = \Theta(g(n)) \iff f(n) = O(g(n))\ \text{and}\ f(n) = \Omega(g(n)).$$

($\Rightarrow$) If $f = \Theta(g)$, there exist $c_1, c_2, n_0$ with $c_1 g \leq f \leq c_2 g$ for $n \geq n_0$. The upper inequality with constant $c = c_2$ gives $f = O(g)$; the lower with $c = c_1$ gives $f = \Omega(g)$.

($\Leftarrow$) If $f = O(g)$ with constant $c_2$ and $n_0' $, and $f = \Omega(g)$ with constant $c_1$ and $n_0''$, then for all $n \geq \max(n_0', n_0'')$ we have $c_1 g \leq f \leq c_2 g$, establishing $f = \Theta(g)$.■

$o$ and $\omega$ — Non-tight Bounds

Definition 3.4 ($o$ and $\omega$)

$f(n) = o(g(n))$ if for every positive constant $c$, there exists $n_0 > 0$ with $0 \leq f(n) < c g(n)$ for all $n \geq n_0$. Equivalently: $\displaystyle\lim_{n \to \infty} \frac{f(n)}{g(n)} = 0$.

$f(n) = \omega(g(n))$ if for every positive constant $c$, there exists $n_0$ with $0 \leq c g(n) < f(n)$ for all $n \geq n_0$. Equivalently: $\displaystyle\lim_{n \to \infty} \frac{f(n)}{g(n)} = \infty$.

A useful analogy: $O$ is "$\leq$", $\Omega$ is "$\geq$", $\Theta$ is "$=$", $o$ is "$<$", and $\omega$ is "$>$". Examples: $2n = o(n^2)$, $n^2/2 \neq o(n^2)$; $n^2 = \omega(n)$, $n^2 \neq \omega(n^2)$.

Properties — Transitivity, Reflexivity, Symmetry

Properties of Asymptotic Notation

Transitivity. For any notation in $\{O, \Theta, \Omega, o, \omega\}$: $$f = \Theta(g)\ \text{and}\ g = \Theta(h) \Rightarrow f = \Theta(h),$$ and analogously for the others.

Reflexivity. $f = \Theta(f)$, $f = O(f)$, $f = \Omega(f)$. (Not $o$ or $\omega$!)

Symmetry. $f = \Theta(g) \iff g = \Theta(f)$.

Transpose symmetry. $f = O(g) \iff g = \Omega(f)$;   $f = o(g) \iff g = \omega(f)$.

Unlike with real numbers, there is no trichotomy for functions: not every pair satisfies one of $f = O(g)$, $f = \Theta(g)$, or $f = \Omega(g)$. A counterexample: $f(n) = n$ and $g(n) = n^{1+\sin n}$. The exponent oscillates, so neither function eventually dominates the other.

Proof Techniques — Worked Problems

Worked Problem 3.1 — Prove $6n^3 \neq \Theta(n^2)$

Suppose for contradiction that $6n^3 = \Theta(n^2)$. Then there exist $c_2, n_0 > 0$ such that $6n^3 \leq c_2 n^2$ for all $n \geq n_0$, i.e. $6n \leq c_2$ for all $n \geq n_0$. But $6n \to \infty$, so this is false. Contradiction.■

Worked Problem 3.2 — Prove $\max(f(n), g(n)) = \Theta(f(n) + g(n))$ for asymptotically nonneg. $f, g$

We need constants $c_1, c_2, n_0$ such that $c_1(f+g) \leq \max(f,g) \leq c_2(f+g)$ for $n \geq n_0$.

Upper bound. Clearly $\max(f,g) \leq f + g$, so $c_2 = 1$ works.

Lower bound. We have $f + g \leq 2 \max(f, g)$, hence $\max(f,g) \geq \tfrac{1}{2}(f + g)$. So $c_1 = \tfrac{1}{2}$ works.

Both bounds hold as soon as both $f, g \geq 0$, which is true for all $n \geq n_0$ by hypothesis.■

3.2Standard Notations and Common Functions

Before leaving growth of functions, we record a catalogue of standard objects — monotonicity, floors and ceilings, modular arithmetic, polynomials, exponentials, logarithms, factorials, and iterated logarithms — together with the comparisons between them that recur constantly in analysis.

Monotonicity

A function $f$ is monotonically increasing if $m \leq n \Rightarrow f(m) \leq f(n)$; strictly increasing if the conclusion is $f(m) < f(n)$; and analogously for decreasing.

Floors and Ceilings

$\lfloor x \rfloor$ is the largest integer $\leq x$, $\lceil x \rceil$ the smallest integer $\geq x$. For all real $x$: $x - 1 < \lfloor x \rfloor \leq x \leq \lceil x \rceil < x + 1$. Both are monotonically increasing. A fact we will use repeatedly: for any integer $n$ and positive integers $a$ and $b$,

$$\left\lceil \frac{\lceil n/a \rceil}{b} \right\rceil = \left\lceil \frac{n}{ab} \right\rceil, \qquad \left\lfloor \frac{\lfloor n/a \rfloor}{b} \right\rfloor = \left\lfloor \frac{n}{ab} \right\rfloor.$$

Polynomials, Exponentials, Logarithms

A polynomial in $n$ of degree $d$ is a function $p(n) = \sum_{i=0}^{d} a_i n^i$ with $a_d \neq 0$. If $a_d > 0$, then $p(n) = \Theta(n^d)$. We say $f(n)$ is polynomially bounded if $f(n) = O(n^k)$ for some constant $k$.

The following inequality captures the key comparison between exponentials and polynomials:

Theorem 3.2 — Exponentials dominate polynomials For any real constants $a > 1$ and $b$, $$\lim_{n \to \infty} \frac{n^b}{a^n} = 0,$$ hence $n^b = o(a^n)$. Equivalently: any polynomial grows asymptotically slower than any exponential with base $> 1$.

A symmetric statement holds for logarithms versus polynomials:

Theorem 3.3 — Polynomials dominate logarithms For any constants $a > 0$ and $b > 0$, $$\lim_{n \to \infty} \frac{\lg^b n}{n^a} = 0,$$ so $\lg^b n = o(n^a)$. (Here $\lg^b n$ means $(\lg n)^b$.)

Taken together, these are the backbone of the algorithm designer's intuition:

constants $\prec$ logs $\prec$ polynomials $\prec$ exponentials $\prec$ factorials.

Factorials — Stirling's Approximation

Stirling's Approximation $$n! = \sqrt{2\pi n} \left(\frac{n}{e}\right)^n \left(1 + \Theta\!\left(\frac{1}{n}\right)\right).$$ As a consequence: $n! = o(n^n)$, $n! = \omega(2^n)$, and $\lg(n!) = \Theta(n \lg n)$.

Functional Iteration and $\log^*$

The notation $f^{(i)}(n)$ means $f$ applied $i$ times to $n$: $f^{(0)}(n) = n$, $f^{(i)}(n) = f(f^{(i-1)}(n))$ for $i \geq 1$. The iterated logarithm is

$$\lg^*(n) = \min\{\, i \geq 0 : \lg^{(i)}(n) \leq 1 \,\}.$$

That is, $\lg^* n$ counts how many times we must apply $\lg$ to $n$ before the result drops to at most $1$. This function grows unimaginably slowly:

$n$$\lg^* n$
$n \leq 1$$0$
$n = 2$$1$
$n \in \{3, 4\}$$2$
$n \in [5, 16]$$3$
$n \in [17, 65536]$$4$
$n \in [65537, 2^{65536}]$$5$

For any conceivable physical input, $\lg^* n \leq 5$. This is why algorithms with running times such as $O(m \cdot \alpha(m, n))$ (where $\alpha$ is the inverse Ackermann function — even slower than $\lg^*$) are said to run in "effectively linear" time.

Chapter 4

Divide & Conquer

When an algorithm is recursive, its running time is naturally expressed as a recurrence — an equation defining $T(n)$ in terms of $T$ at smaller values. This chapter develops three techniques for solving such recurrences: the substitution method (guess and prove by induction), the recursion-tree method (sum work level-by-level to generate a guess), and the master method (apply a theorem). In practice one often uses the recursion tree to guess, then the substitution method to prove, or — when applicable — skips directly to the master theorem.

4.3The Substitution Method

The substitution method has two steps:

  1. Guess the form of the solution.
  2. Use mathematical induction to find the constants and show that the solution works.

The name comes from substituting the guessed solution for the function when the inductive hypothesis is applied to smaller values.

Worked Example — Solving $T(n) = 2T(\lfloor n/2 \rfloor) + n$

We will show that $T(n) = O(n \lg n)$. (Observe that this is the merge-sort recurrence up to notation.)

Claim If $T(1) = \Theta(1)$ and $T(n) = 2T(\lfloor n/2 \rfloor) + n$ for $n > 1$, then $T(n) = O(n \lg n)$.

Guess. $T(n) \leq c n \lg n$ for some constant $c > 0$ and all $n \geq n_0$.

Inductive step. Assume the bound holds for all values $m < n$ (with $m \geq n_0$). We show it holds for $n$. By the recurrence, $$T(n) = 2T(\lfloor n/2 \rfloor) + n.$$ Applying the inductive hypothesis to $\lfloor n/2 \rfloor$: $$T(n) \leq 2 \cdot c \lfloor n/2 \rfloor \lg(\lfloor n/2 \rfloor) + n \leq 2 \cdot c \cdot (n/2) \cdot \lg(n/2) + n = c n \lg(n/2) + n.$$ Since $\lg(n/2) = \lg n - 1$, $$T(n) \leq c n \lg n - c n + n = c n \lg n - (c - 1) n.$$ For the desired bound $T(n) \leq c n \lg n$, we need $(c - 1) n \geq 0$, i.e. $c \geq 1$.

Base case. We need $n_0$ for which the induction can start. Taking $n_0 = 2$ and any $c \geq T(2)/(2 \lg 2) = T(2)/2$ ensures $T(2) \leq c \cdot 2 \lg 2 = 2c$. (We cannot use $n = 1$ as a base case because $\lg 1 = 0$ and the bound $c \cdot 1 \cdot \lg 1 = 0$ would require $T(1) = 0$. This is why substitution proofs typically take the smallest two values as base cases.) Taking $c = \max(1, T(2)/2)$ completes the argument.■

The Art of Making a Good Guess

There is no recipe — experience and the recursion-tree method (§4.4) are the two chief sources of guesses. When one recurrence resembles another whose solution is known, the known solution is a natural first guess. For example:

  • $T(n) = 2T(\lfloor n/2 \rfloor + 17) + n$ looks like merge sort — guess $O(n \lg n)$; the $+17$ perturbation is asymptotically irrelevant.
  • If loose bounds are known ($T = \Omega(n)$ and $T = O(n^2)$), work inward: first refine the lower bound to $\Omega(n \lg n)$, then the upper to $O(n \lg n)$.

Subtleties — The Need for Stronger Induction Hypotheses

Sometimes the obvious guess cannot be proved even though it is correct. Consider

$$T(n) = T(\lfloor n/2 \rfloor) + T(\lceil n/2 \rceil) + 1.$$

We might guess $T(n) = O(n)$, and attempt to prove $T(n) \leq c n$. Then $$T(n) \leq c \lfloor n/2 \rfloor + c \lceil n/2 \rceil + 1 = c n + 1,$$ which is not $\leq c n$. The induction fails — but the guess is right! The fix is to strengthen the hypothesis by subtracting a lower-order term: guess $T(n) \leq c n - d$ for constants $c, d > 0$. Then

$$T(n) \leq (c \lfloor n/2 \rfloor - d) + (c \lceil n/2 \rceil - d) + 1 = c n - 2d + 1 \leq c n - d$$

as long as $d \geq 1$. The stronger hypothesis is easier to prove because it leaves more "slack" to absorb the additive $+1$.

Pitfalls

Never conclude $T(n) = O(n)$ from an argument of the form

$T(n) \leq 2(c \lfloor n/2 \rfloor) + n = c n + n = O(n)$.

This is wrong. The inductive step must produce exactly the form of the hypothesis $T(m) \leq c m$ — with the same constant $c$ — not merely some $O(n)$ expression. Constants must be pinned down explicitly.

4.4The Recursion-Tree Method

In a recursion tree, each node represents the cost of a single subproblem in the set of recursive function invocations. We sum the costs within each level to obtain a per-level total, then sum those over all levels. The recursion tree is especially good at generating a guess that we can then verify by the substitution method.

Case Study — Merge Sort, Revisited

Recall $T(n) = 2T(n/2) + cn$ for $n > 1$ (with $c$ some constant), $T(1) = c$. Assume for exposition that $n$ is a power of $2$.

Recursion Tree for Merge Sort

Level 0 (the root) does $cn$ work and has $1$ node.

Level 1 has $2$ nodes, each doing $c(n/2)$ work — total: $cn$.

Level 2 has $4$ nodes, each doing $c(n/4)$ work — total: $cn$.

Level $i$ has $2^i$ nodes, each doing $c(n/2^i)$ work — total: $cn$.

The recursion bottoms out at subproblem size $1$, which happens at level $\lg n$.

There are thus $\lg n + 1$ levels, each contributing $cn$ work: $$T(n) = cn (\lg n + 1) = cn \lg n + cn = \Theta(n \lg n).$$

A Harder Example — $T(n) = 3T(n/4) + cn^2$

Let's use the recursion tree to guess a solution, then verify by substitution.

Level-by-level Cost

The root has cost $cn^2$ and $3$ children of size $n/4$; those children have $9$ grandchildren of size $n/16$; and so on. At level $i$ there are $3^i$ nodes, each with cost $c(n/4^i)^2 = c n^2 / 16^i$. The per-level cost is $$3^i \cdot \frac{c n^2}{16^i} = \left(\frac{3}{16}\right)^i c n^2.$$

The tree has depth $\log_4 n$ (since subproblem size $n/4^i = 1$ when $i = \log_4 n$). Summing the per-level costs: $$T(n) = \sum_{i=0}^{\log_4 n - 1} \left(\frac{3}{16}\right)^i c n^2 + \Theta(n^{\log_4 3}).$$ The final additive term is the total cost of the leaves: there are $3^{\log_4 n} = n^{\log_4 3}$ leaves, each costing $\Theta(1)$.

Since $3/16 < 1$, the geometric sum is bounded above by $\sum_{i=0}^{\infty} (3/16)^i c n^2 = \frac{c n^2}{1 - 3/16} = \frac{16}{13} c n^2$. Thus $T(n) = O(n^2)$. The leaf contribution $n^{\log_4 3} \approx n^{0.79}$ is dominated by $n^2$.

We verify by substitution: guess $T(n) \leq d n^2$. The recurrence gives $T(n) \leq 3 d (n/4)^2 + c n^2 = \tfrac{3}{16} d n^2 + c n^2 = (\tfrac{3}{16} d + c) n^2.$ We want this $\leq d n^2$, i.e. $\tfrac{3}{16} d + c \leq d$, i.e. $d \geq \tfrac{16}{13} c$. So choose $d = \tfrac{16}{13} c$ and the bound holds. Conclusion: $T(n) = O(n^2)$ — and a matching lower bound from the root term gives $T(n) = \Theta(n^2)$.

Unbalanced Splits — $T(n) = T(n/3) + T(2n/3) + cn$

Here subproblem sizes shrink at different rates. The longest root-to-leaf path goes through the $2/3$-children at each step; it reaches size $1$ when $(2/3)^k n = 1$, i.e. $k = \log_{3/2} n$. The shortest path goes through the $1/3$-children and has length $\log_3 n$. For a full tree (before any leaf is reached), each level sums to $cn$: a subproblem of size $m$ contributes $cm$, and the subproblems at each level partition the original $n$. So for at least the first $\log_3 n$ levels the per-level total is exactly $cn$. The upper bound is $T(n) = O(cn \log_{3/2} n) = O(n \lg n)$; a matching lower bound from counting the "full" part gives $T(n) = \Omega(n \lg n)$, so $T(n) = \Theta(n \lg n)$.

4.5The Master Method

The master method is a cookbook for recurrences of the form $$T(n) = a T(n/b) + f(n), \qquad a \geq 1, \quad b > 1, \quad f(n) \text{ asymptotically positive}.$$ Here the problem of size $n$ is divided into $a$ subproblems of size $n/b$, and $f(n)$ is the cost of the divide and combine steps. (We interpret $n/b$ as either $\lfloor n/b \rfloor$ or $\lceil n/b \rceil$ throughout — the asymptotic answer is the same.)

Theorem 4.1 — The Master Theorem (CLRS) Let $a \geq 1$ and $b > 1$ be constants, let $f(n)$ be an asymptotically positive function, and let $T(n)$ be defined by $$T(n) = a T(n/b) + f(n).$$ Define the watershed function $n^{\log_b a}$. Then $T(n)$ has the following asymptotic bounds:
  1. Case 1. If $f(n) = O(n^{\log_b a - \varepsilon})$ for some constant $\varepsilon > 0$, then $T(n) = \Theta(n^{\log_b a})$.
  2. Case 2. If $f(n) = \Theta(n^{\log_b a})$, then $T(n) = \Theta(n^{\log_b a} \lg n)$.
  3. Case 3. If $f(n) = \Omega(n^{\log_b a + \varepsilon})$ for some constant $\varepsilon > 0$, and if $a f(n/b) \leq c f(n)$ for some constant $c < 1$ and all sufficiently large $n$ (the regularity condition), then $T(n) = \Theta(f(n))$.

Interpretation

The watershed $n^{\log_b a}$ is the cost contributed by the leaves of the recursion tree: there are $a^{\log_b n} = n^{\log_b a}$ of them, each of $\Theta(1)$ cost.

  • Case 1. $f$ is polynomially smaller than the watershed — leaves dominate, $T(n) = \Theta(n^{\log_b a})$.
  • Case 2. $f$ matches the watershed up to constants — all levels are equal, add an extra $\lg n$ factor, $T(n) = \Theta(n^{\log_b a} \lg n)$.
  • Case 3. $f$ is polynomially larger than the watershed and regular — the root dominates, $T(n) = \Theta(f(n))$.
The word "polynomially" is essential. $f(n) = n^{\log_b a} / \lg n$ is asymptotically smaller than $n^{\log_b a}$, but not polynomially so. In this gap, none of the three cases applies. Similarly $f(n) = n^{\log_b a} \lg n$ sits in a gap above Case 2.

$a = 7, b = 2$, $\log_b a = \lg 7 \approx 2.807$. $f(n) = n^2 = O(n^{\lg 7 - \varepsilon})$ for, say, $\varepsilon = 0.8$. Case 1: $T(n) = \Theta(n^{\lg 7})$. This is the celebrated $O(n^{2.81})$ matrix-multiplication bound.

A Case-3 Example — $T(n) = 3 T(n/4) + n \lg n$

$\log_b a = \log_4 3 \approx 0.793$, watershed $n^{0.793}$. $f(n) = n \lg n = \Omega(n^{0.793 + \varepsilon})$ for, say, $\varepsilon = 0.1$. We verify regularity: $a f(n/b) = 3 \cdot (n/4)\lg(n/4) = (3/4) n \lg n - (3/4) n \lg 4 \leq (3/4) n \lg n = (3/4) f(n)$ for large $n$, with $c = 3/4 < 1$. Case 3: $T(n) = \Theta(n \lg n)$.

A Gap Example — $T(n) = 2 T(n/2) + n \lg n$

$\log_b a = 1$, watershed $n$. $f(n) = n \lg n$. Is $n \lg n = \Omega(n^{1+\varepsilon})$ for some $\varepsilon > 0$? No: $\lg n = o(n^\varepsilon)$ for every $\varepsilon > 0$. So we are in the gap between Cases 2 and 3, and the master theorem does not apply. A different technique — recursion tree or substitution — gives $T(n) = \Theta(n \lg^2 n)$.

Chapter 5

Probabilistic Analysis & Randomized Algorithms

Up to now, running time has been a function of the input alone. In this chapter we introduce two deeply related but conceptually distinct ideas. Probabilistic analysis assumes a distribution over inputs and computes expected running time. A randomized algorithm, by contrast, makes no assumption about the input: instead, the algorithm itself flips coins, and the distribution is over the algorithm's internal choices. The distinction matters — an adversary can supply worst-case input, but cannot predict an algorithm's coin flips.

Throughout this chapter we assume basic familiarity with discrete probability: a sample space, events, probabilities, random variables, and expectation $\operatorname{E}[X] = \sum_x x \cdot \Pr[X = x]$. The single most important tool we develop is the indicator random variable, which converts probability computations into expectation computations via linearity of expectation.

5.1The Hiring Problem

You run an employment agency. Every day the agency sends you one candidate for office assistant. You interview the candidate at cost $c_\text{i}$ (small). If the new candidate is better than the current assistant, you hire them — firing the incumbent and paying the much larger cost $c_\text{h}$. You will interview all $n$ candidates, but how many will you end up hiring?

Why should we care about this particular story?

The hiring problem is a stand-in for a whole class of online algorithms — ones that must commit to decisions one element at a time, without seeing the future. It also captures the pattern "find the running maximum" that appears everywhere: tracking the best bid in an auction, the largest packet seen by a network switch, the peak value in a data stream. The cost structure — cheap to look, expensive to commit — is the whole point.

The worst case is terrible (pay $c_\text{h}$ every single day). The best case is wonderful (pay it exactly once). So worst-case analysis would scare you away from this algorithm. The fix is to stop asking "how bad can it be?" and ask instead "how bad is it on average?"

Hire-Assistant
1 best = 0 // candidate 0 is a dummy "least qualified" 2 for $i = 1$ to $n$ 3 interview candidate $i$ 4 if candidate $i$ is better than candidate best 5 best = $i$ 6 hire candidate $i$

The cost breakdown is $c_\text{i} n + c_\text{h} m$, where $m$ is the number of hires. The interview cost is fixed, so the question reduces to: what is $m$?

Worst & best cases
If the candidates arrive in strictly increasing order of quality, $m = n$ and the cost is $\Theta(n \cdot c_\text{h})$. If the best candidate arrives first, $m = 1$. The worst case is catastrophic; we want the expected value of $m$.
Before we compute anything, guess

If I told you there are $n = 10$ candidates and they arrive in random order, how many hires do you expect? Most people guess something like $5$ — half, roughly. The real answer for $n = 10$ is about $2.93$. For $n = 1000$ it's about $7.49$. For $n = 10^6$ it's about $14.4$. Hiring grows like $\ln n$, not $n$, not $\sqrt{n}$, not $\lg n$ — the natural logarithm. That is the striking result we are about to prove.

The reason, roughly, is that early candidates beat an empty résumé stack and are usually hired; but as the "best so far" climbs, each new candidate has a smaller and smaller chance of topping it. So the hiring rate crashes like $1/i$, and summing those probabilities yields the harmonic number $H_n$.

Theorem 5.1 (Expected number of hires)
Assuming the candidates arrive in a uniformly random order (a uniform random permutation of $n$ distinct ranks), the expected cost of Hire-Assistant is $O(c_\text{h} \ln n)$. More precisely, the expected number of hires is $H_n = \sum_{k=1}^{n} 1/k = \ln n + O(1)$.
Proof sketch (full argument in §5.2)

Here is the whole argument in one sentence: candidate $i$ is hired iff they are the best of the first $i$ arrivals; under a random permutation that happens with probability $1/i$; summing gives $H_n$. The two moves that make this proof so short are (1) turning "count hires" into a sum of 0/1 variables, one per candidate, and (2) exploiting symmetry to get each probability for free.

Formally. Let $X$ be the total number of hires. Define indicator $X_i = \mathbb{1}\{\text{candidate }i\text{ is hired}\}$, so $X = \sum_{i=1}^n X_i$. Candidate $i$ is hired iff they are better than all of candidates $1, \ldots, i-1$ — that is, iff they are the maximum of the first $i$ arrivals. Under a uniform random permutation every element is equally likely to be the max of any prefix, so $\Pr[X_i = 1] = 1/i$ and hence $\operatorname{E}[X_i] = 1/i$. By linearity, $\operatorname{E}[X] = \sum_i 1/i = H_n = \ln n + O(1)$. $\blacksquare$

The key insight — which we develop rigorously in §5.2 — is that we did not need the joint distribution of the $X_i$'s. Linearity of expectation holds regardless of dependence, and this is what makes the calculation tractable: the $X_i$'s are in fact highly correlated (hiring candidate $i$ makes it harder to hire candidate $i+1$), but we never had to untangle that mess.

5.2Indicator Random Variables

We now develop the tool used above. The technique is simple to state but extraordinarily powerful — it reduces almost every expected-value calculation in this book to a sum of probabilities.

The trick in one idea

Suppose you want to count something random — hires, heads, inversions, compared pairs — and compute its expectation. The naive approach stares at the full distribution of the count, which usually looks horrible. The clever approach: write the count as a sum of tiny 0/1 variables (one per "thing" you might be counting) and add up their individual probabilities. Because expectation is linear, that sum of probabilities is the expectation — no joint distribution required.

The part that looks like cheating is this: even if the tiny 0/1 variables are highly dependent, the trick still works. Dependence does not leak into the expectation of a sum. This is why hand-written proofs that would take pages of conditioning collapse into two lines of arithmetic.

Definition 5.1 — Indicator random variable
Given a sample space $S$ and an event $A \subseteq S$, the indicator random variable $I\{A\}$ is defined as $$I\{A\} = \begin{cases} 1 & \text{if $A$ occurs,} \\ 0 & \text{if $A$ does not occur.}\end{cases}$$
Lemma 5.1 (Expectation of an indicator)
Given an event $A$, let $X_A = I\{A\}$. Then $\operatorname{E}[X_A] = \Pr[A]$.
Proof
By the definition of expectation for a discrete random variable, $$\operatorname{E}[X_A] = 1 \cdot \Pr[A] + 0 \cdot \Pr[\bar{A}] = \Pr[A]. \qquad\blacksquare$$
Theorem 5.2 (Linearity of expectation)
For any random variables $X_1, \ldots, X_n$, defined on the same sample space, $$\operatorname{E}\!\left[\sum_{i=1}^n X_i\right] = \sum_{i=1}^n \operatorname{E}[X_i].$$ This holds even when the $X_i$ are not independent.
Why linearity works even for correlated variables

If you tried to prove $\operatorname{E}[X+Y] = \operatorname{E}[X] + \operatorname{E}[Y]$ from the joint distribution, you'd write $$\operatorname{E}[X+Y] = \sum_{x,y}(x+y)\Pr[X=x, Y=y] = \sum_{x,y} x \Pr[X=x,Y=y] + \sum_{x,y} y \Pr[X=x,Y=y].$$ Now marginalize: $\sum_y \Pr[X=x,Y=y] = \Pr[X=x]$ regardless of what $Y$ is doing — that's the definition of a marginal. So the two terms collapse to $\sum_x x \Pr[X=x] + \sum_y y \Pr[Y=y] = \operatorname{E}[X]+\operatorname{E}[Y]$.

The entire argument never used independence. Dependence controls products of random variables (that's why $\operatorname{E}[XY] = \operatorname{E}[X]\operatorname{E}[Y]$ needs independence), not sums. Linearity is a consequence of being able to separate sums, and sums separate unconditionally.

Linearity is the workhorse. Combined with Lemma 5.1, it gives a two-step recipe: (i) write the quantity of interest as a sum of indicators $X = \sum X_i$; (ii) compute each $\Pr[X_i = 1]$ separately (ignoring correlations); then $\operatorname{E}[X] = \sum \Pr[X_i = 1]$.

The recipe, applied

Whenever you see a problem asking "what is the expected number of X?" try this four-step template:

  1. Identify what is being counted. Assign one indicator variable per countable "slot" (one per candidate, one per pair, one per coin...).
  2. Define the indicator event precisely — "candidate $i$ is the max so far", "pair $(i,j)$ is an inversion", "coin $i$ shows heads".
  3. Compute each indicator's probability, one at a time, leaning on symmetry when possible. Do not worry about joint behaviour.
  4. Sum the probabilities. That number is $\operatorname{E}[\text{total count}]$.

All three examples below are just this template applied to different slots.

Example 5.1 — Hiring problem, re-derived
Let $X_i$ indicate that candidate $i$ is hired. Candidate $i$ is hired iff $A_i$ = "candidate $i$ has the highest rank among the first $i$". Among $\{1, \ldots, i\}$ the max position is uniformly distributed, so $\Pr[A_i] = 1/i$. Thus $$\operatorname{E}[\text{hires}] = \operatorname{E}\!\left[\sum_{i=1}^n X_i\right] = \sum_{i=1}^n \operatorname{E}[X_i] = \sum_{i=1}^n \frac{1}{i} = H_n.$$
Example 5.2 — Expected number of coin-flip heads
Flip $n$ fair coins. Let $X_i = I\{\text{coin }i\text{ shows heads}\}$, so $X = \sum X_i$ is the total heads. Each $\operatorname{E}[X_i] = \Pr[\text{heads}] = 1/2$, hence $\operatorname{E}[X] = n/2$. Note: this derivation never mentions the binomial distribution.
Example 5.3 — Expected inversions in a random permutation
Let $A[1\mathinner{.\,.}n]$ be a uniform random permutation. An inversion is a pair $(i,j)$ with $i < j$ and $A[i] > A[j]$. Let $X_{ij} = I\{A[i] > A[j]\}$. For any two positions, each relative order is equally likely, so $\operatorname{E}[X_{ij}] = 1/2$. The total number of pairs is $\binom{n}{2}$, so $$\operatorname{E}[\text{inversions}] = \binom{n}{2} \cdot \frac{1}{2} = \frac{n(n-1)}{4}.$$ This gives the expected running time of insertion sort on a random permutation: $\Theta(n^2)$, unchanged from the worst case. Notice how astonishingly direct this was — no generating functions, no recursion, no clever bijection. Two sentences.

5.3Randomized Algorithms

In the probabilistic analysis above, we assumed the adversary (who supplies the input) obeys a specific distribution. This is often unrealistic. The fix: we make the algorithm random. A randomized algorithm makes decisions based on the output of a random-number generator, so its running time becomes a random variable even for a fixed, adversarially chosen input.

The algorithm-vs-adversary game

Picture it as a two-player game. The adversary wants to make the algorithm slow; the algorithm wants to be fast. Worst-case analysis is what happens when the adversary always wins: they pick the nastiest possible input and the algorithm has no recourse.

Probabilistic analysis neutralizes the adversary by assumption: we decree that inputs come from some distribution, so the adversary cannot pick them. That's a strong assumption, and it breaks the moment a real attacker notices our algorithm.

Randomization flips the script. We make the algorithm unpredictable, so the adversary can no longer target any particular execution. They can still pick any input they like — it doesn't matter, because which code paths we take depends on coins we flip, not on them. For any fixed input, the running time is now distributed exactly the same way. The adversary has nothing left to exploit.

Primitive assumption
We assume access to a primitive Random$(a,b)$ returning a uniformly random integer in $[a, b]$, in $O(1)$ expected time. Implementing such a primitive from a truly random bit source is itself a subtle problem; we take it for granted.

For the hiring problem, the randomized version is simple: permute the input before running Hire-Assistant. This decouples the running time from the adversary's input choice and makes $\operatorname{E}[\text{hires}] = H_n$ regardless of the input order.

Permuting an array in place

Two algorithms produce a uniform random permutation. The first — via sorting by random keys — is conceptually clean but slow. The second — the Fisher–Yates shuffle — runs in $\Theta(n)$ and is the one to remember.

Randomize-In-Place($A$)   // Fisher–Yates
1 $n$ = $A$.length 2 for $i = 1$ to $n$ 3 swap $A[i]$ with $A[\textsc{Random}(i, n)]$
Theorem 5.3 (Fisher–Yates produces a uniform random permutation)
After Randomize-In-Place terminates, each of the $n!$ permutations of the input appears with probability exactly $1/n!$.
Proof (loop-invariant)

Invariant. At the start of each iteration of the for-loop (line 2), for every possible $(i-1)$-permutation $\sigma$ of $(i-1)$ elements drawn from $A$, the subarray $A[1\mathinner{.\,.}i-1]$ equals $\sigma$ with probability $(n-i+1)!/n!$.

Initialization ($i=1$). The empty $0$-permutation occurs with probability $1 = n!/n!$. $\checkmark$

Maintenance. Assume the invariant at the start of iteration $i$: any specific $(i-1)$-permutation has probability $(n-i+1)!/n!$ of being the current $A[1\mathinner{.\,.}i-1]$. In iteration $i$, we swap $A[i]$ with a uniformly chosen $A[k]$ for $k \in \{i, \ldots, n\}$. For a target $i$-permutation $\tau$ whose first $i-1$ entries form $\sigma$ and whose $i$-th entry is some value $v$, we have $$\Pr[A[1\mathinner{.\,.}i] = \tau] = \Pr[\text{first }i-1\text{ entries} = \sigma] \cdot \Pr[\text{swap places }v\text{ at position }i \mid \sigma]$$ $$= \frac{(n-i+1)!}{n!} \cdot \frac{1}{n-i+1} = \frac{(n-i)!}{n!}.$$ This matches the invariant for $i+1$. $\checkmark$

Termination ($i = n+1$). The invariant says each full $n$-permutation has probability $0!/n! = 1/n!$. $\blacksquare$

A common bug
In line 3, the range is $\textsc{Random}(i, n)$ — inclusive of $i$. A popular mistake is to use $\textsc{Random}(1, n)$ or $\textsc{Random}(i+1, n)$; both yield a non-uniform distribution. (Exercise: prove the former produces each permutation with probability some multiple of $n^{-n}$, which is generally not of the form $1/n!$.)

Heapsort

Heapsort is the first sorting algorithm we meet that runs in $\Theta(n \lg n)$ worst case and in-place — combining the asymptotic guarantee of merge sort with the memory discipline of insertion sort. It introduces the heap, a data structure that will reappear as a priority queue throughout the book. The heap is not merely a device for sorting; it is one of the most useful data structures in the practical programmer's toolkit.

6.1Heaps

The picture to hold in your head

A heap is a binary tree squashed into an array. It has just two rules:

  1. Shape: fill the tree level by level, left to right, with no gaps. The last level might be incomplete on the right — that's fine — but no node higher up can be missing.
  2. Order (max-heap): every parent is $\ge$ its children.

Rule 1 makes the tree tight — height is always $\lfloor \lg n \rfloor$. Rule 2 pins the maximum at the root. That's it. Every heap algorithm in this chapter is some way of maintaining these two invariants while inserting, extracting, or reorganizing elements.

The "array storage" trick is what makes heaps fast in practice. Because the shape is so constrained, we never need pointers: child, parent, and sibling are all one quick arithmetic operation on the index. The tree exists only in our imagination; on the machine it's a flat array, dense and cache-friendly.

Definition 6.1 — (Binary) heap
A (binary) heap is an array $A[1\mathinner{.\,.}n]$, viewed as a nearly-complete binary tree, where:
  • The tree is nearly complete: every level except possibly the last is full, and the last level is filled from left to right.
  • The array encodes the tree using $A.\text{heap-size} \le A.\text{length}$, with the root at index 1 and the navigation functions: $$\textsc{Parent}(i) = \lfloor i/2 \rfloor, \qquad \textsc{Left}(i) = 2i, \qquad \textsc{Right}(i) = 2i+1.$$
Why $2i$ and $2i+1$?
Write $i$ in binary. The root is $1_2$. Appending a $0$ goes to the left child ($2i$); appending a $1$ goes to the right child ($2i+1$); stripping the last bit goes to the parent ($\lfloor i/2 \rfloor$). In other words, the binary expansion of an index literally spells out the path from the root. Level $k$ contains exactly the indices whose binary expansions have $k+1$ bits.
Definition 6.2 — Max-heap & min-heap properties
A max-heap satisfies: for every $i$ other than the root, $$A[\textsc{Parent}(i)] \ge A[i].$$ Equivalently, every subtree's root is greater-or-equal to all its descendants. A min-heap reverses the inequality: $A[\textsc{Parent}(i)] \le A[i]$. Heapsort uses max-heaps; priority queues typically use min-heaps.
Lemma 6.1 (Structural facts)
Let $A$ be a heap of size $n$. Then:
  1. The height of the tree is $\lfloor \lg n \rfloor = \Theta(\lg n)$.
  2. A heap of $n$ elements has at most $\lceil n/2^{h+1} \rceil$ nodes of height $h$.
  3. The leaves are exactly the nodes at indices $\lfloor n/2 \rfloor + 1, \ldots, n$.
Proof of (3)
A node at index $i$ is a leaf iff it has no left child, i.e. $\textsc{Left}(i) = 2i > n$. Solving: $i > n/2$, i.e. $i \ge \lfloor n/2 \rfloor + 1$. $\blacksquare$
Fact (3) in plain English
Half the elements are leaves. This is the single most important structural fact about heaps. It is why "building a heap" takes $O(n)$ rather than $O(n \lg n)$: the cheap work (leaves, no-ops) dominates the count; the expensive work (root, $\Theta(\lg n)$) is done only once. We'll cash in this observation formally in §6.3.

The array representation is crucial: it requires no pointers, it uses memory proportional exactly to the number of elements, and parent/child navigation is constant-time arithmetic. On real hardware, the cache locality dramatically outperforms pointer-based trees.

6.2Maintaining the Heap Property

The fundamental heap operation is Max-Heapify$(A, i)$: given an index $i$ whose children are already max-heaps but whose value may be smaller than a child, "sift down" $A[i]$ until the subtree rooted at $i$ is a max-heap. This is the operation we'll compose to build heaps and extract maxima.

What "sift down" means, physically

Imagine the node at $i$ is a ball that's lighter than it should be — a small value stuck at a high position. Gravity wants to pull it down. At each step, look at the ball's two children. If one of them is heavier (bigger value), swap — the ball sinks one level. Repeat. It stops when the ball is heavier than both children, or when it becomes a leaf.

The key precondition is that the children's subtrees are already correct max-heaps. All we're fixing is the one misplaced element at the top. At each level the ball either settles or keeps sinking, so the total work is at most the tree height: $O(\lg n)$.

Warning: Max-Heapify is local. If the array is chaotic to begin with, calling Max-Heapify at the root does not produce a max-heap. The algorithm relies on its precondition. To turn a garbage array into a heap, we'll call Max-Heapify bottom-up — §6.3.

Max-Heapify($A$, $i$)
1 $l$ = Left($i$) 2 $r$ = Right($i$) 3 if $l \le A.\text{heap-size}$ and $A[l] > A[i]$ 4 largest = $l$ 5 else largest = $i$ 6 if $r \le A.\text{heap-size}$ and $A[r] > A[\text{largest}]$ 7 largest = $r$ 8 if largest $\ne i$ 9 swap $A[i]$ with $A[\text{largest}]$ 10 Max-Heapify($A$, largest)

Lines 3–7 identify the largest of three values: the node and its two (possibly absent) children. Line 9 swaps the node with the largest child if it isn't already on top. Line 10 recurses on the child we just demoted the value into — the only subtree whose root may now be out of place.

Theorem 6.2 (Correctness of Max-Heapify)
If the subtrees rooted at $\textsc{Left}(i)$ and $\textsc{Right}(i)$ are max-heaps, then after Max-Heapify$(A, i)$ the subtree rooted at $i$ is a max-heap.
Proof
Induction on the height of the subtree at $i$. Base case: if $i$ is a leaf, both children conditions fail, largest $= i$, and no work is done — the leaf subtree is trivially a heap. Inductive step: among $\{i, l, r\}$, lines 3–7 correctly identify the index of the maximum value. If largest $= i$, the heap property already holds at $i$ (since both subtrees are heaps by hypothesis). Otherwise the swap in line 9 installs the maximum at $i$, and the subtree at largest — whose root has decreased — may now violate the property. But its children are unchanged and still max-heaps, so by the inductive hypothesis the recursive call restores the property. $\blacksquare$
Theorem 6.3 (Running time)
Max-Heapify on a subtree of size $n$ runs in $O(\lg n)$ time.
Proof
Each recursive call moves to a child subtree, which has size at most $2n/3$ (the worst case arises when the bottom level is exactly half full). The work at each level is $\Theta(1)$. Thus $$T(n) \le T(2n/3) + \Theta(1) \underset{\text{master, Case 2}}{=} \Theta(\lg n). \qquad \blacksquare$$

The $2n/3$ bound is a little delicate. When the last row is half-full, the left subtree's size is maximized relative to the right: one can check that $|T_L| = 2n/3$ is achieved. Since we recurse into only one child, this is an upper bound on the recursive subproblem.

6.3Building a Heap

We can convert an arbitrary array into a max-heap by calling Max-Heapify bottom-up. The leaves (indices $\lfloor n/2 \rfloor + 1, \ldots, n$) are already $1$-element heaps, so we start at $\lfloor n/2 \rfloor$ and work backwards.

Why bottom-up?
Max-Heapify's precondition is "the children's subtrees are already max-heaps." If we process nodes top-down we'd violate that immediately. Bottom-up guarantees the precondition by construction: when we reach node $i$, everything below $i$ has already been fixed, so the children are valid max-heaps. It's a textbook instance of working in dependency order.
Build-Max-Heap($A$)
1 $A.\text{heap-size}$ = $A$.length 2 for $i = \lfloor A.\text{length}/2 \rfloor$ downto $1$ 3 Max-Heapify($A$, $i$)
Theorem 6.4 (Correctness)
After Build-Max-Heap terminates, $A[1\mathinner{.\,.}n]$ is a max-heap.
Proof
Invariant. At the start of each iteration of the for-loop, each node $i+1, i+2, \ldots, n$ is the root of a max-heap.
Init. At $i = \lfloor n/2 \rfloor$, nodes $\lfloor n/2 \rfloor + 1, \ldots, n$ are leaves — trivially max-heaps.
Maintenance. By the invariant, the children of $i$ are roots of max-heaps; Max-Heapify$(A, i)$ therefore makes $i$ a max-heap root, while leaving nodes $i+1, \ldots, n$ (untouched) as max-heaps.
Termination. At $i = 0$, node $1$ is a max-heap root — i.e. $A$ is a max-heap. $\blacksquare$
Theorem 6.5 (Tight running time)
Build-Max-Heap runs in $O(n)$ — not $O(n \lg n)$.
Why $O(n)$ is believable (before we prove it)

Here is the one-sentence pitch: the expensive Max-Heapify calls are rare, and the cheap ones are plentiful, and together they telescope.

Picture the heap tree. The root (at height $\lg n$) costs $\Theta(\lg n)$ for one call. Its two children (height $\lg n - 1$) cost $\Theta(\lg n - 1)$ each — two of them. Continue halving: $4$ nodes at height $\lg n - 2$, each costing $\Theta(\lg n - 2)$. At the very bottom, $n/2$ leaves cost $\Theta(1)$ each.

So the total cost is roughly $\sum_h (\text{nodes at height } h) \cdot h \approx \sum_h \frac{n}{2^{h+1}} \cdot h = \frac{n}{2}\sum_h h/2^h$. The tail $\sum h/2^h$ is a fixed constant (equal to $2$). So total work $= \Theta(n) \cdot \text{constant} = \Theta(n)$.

The naive analysis "$n$ calls times $\lg n$ work" is wrong because it pretends every call does $\lg n$ work. In reality, the median call does zero work (half the nodes are leaves). The geometric decay of cost with height is what saves us an entire log factor.

Proof (the clever summation)

A naive upper bound is $n$ calls to Max-Heapify at $O(\lg n)$ each: $O(n \lg n)$. This is loose, because most nodes are near the bottom of the tree and their calls take $O(1)$. The right analysis groups nodes by height.

Recall Lemma 6.1(2): a heap of size $n$ has at most $\lceil n/2^{h+1} \rceil$ nodes of height $h$, and the work of Max-Heapify on a height-$h$ node is $O(h)$. So the total work is $$T(n) \le \sum_{h=0}^{\lfloor \lg n \rfloor} \left\lceil \frac{n}{2^{h+1}} \right\rceil \cdot O(h) = O\!\left(n \sum_{h=0}^{\infty} \frac{h}{2^h}\right).$$ The tail sum converges: $\sum_{h \ge 0} h \cdot x^h = x/(1-x)^2$ for $|x| < 1$. At $x = 1/2$, this gives $(1/2)/(1/4) = 2$. Hence $T(n) \le O(2n) = O(n)$. $\quad\blacksquare$

Why this matters
This is the first non-trivial asymptotic analysis in the book. It shows how a careful weighting by "depth class" can tighten a summation that naive bounding would dramatically overestimate. The technique recurs in the amortized analysis of data structures.

6.4The Heapsort Algorithm

With Build-Max-Heap and Max-Heapify in hand, heapsort is immediate. The root of a max-heap holds the maximum; swap it with the last element, shrink the heap by 1, and restore the property with one Max-Heapify. Repeat.

Heapsort in one sentence

Repeatedly move the root (the max) to the back, shrink the heap, and sift the new root down. After $n - 1$ such swaps the heap is empty and the array is sorted in place.

The array is split into two regions that grow in opposite directions: the active heap at the front (shrinking) and the sorted suffix at the back (growing). Each extraction costs $\Theta(\lg n)$; we do $n-1$ of them; total $\Theta(n \lg n)$. The one-time $O(n)$ Build-Max-Heap is noise in comparison.

Heapsort($A$)
1 Build-Max-Heap($A$) 2 for $i = A$.length downto $2$ 3 swap $A[1]$ with $A[i]$ 4 $A.\text{heap-size}$ = $A.\text{heap-size} - 1$ 5 Max-Heapify($A$, $1$)
Theorem 6.6 (Correctness & complexity)
Heapsort sorts the array $A$ in non-decreasing order and runs in $O(n \lg n)$ worst case.
Proof

Correctness invariant. At the start of each iteration of line 2 with loop variable $i$: (a) $A[1\mathinner{.\,.}i]$ is a max-heap containing the $i$ smallest elements of the original array, and (b) $A[i+1\mathinner{.\,.}n]$ contains the $n-i$ largest elements of the original array, in sorted order.

Init: $i = n$, the full heap, sorted suffix is empty. Maintenance: the swap places the current max $A[1]$ at position $i$, extending the sorted suffix; the heap-size decrement removes it from the active heap; Max-Heapify$(A, 1)$ restores the heap property on the smaller heap. Termination at $i = 1$: $A[1]$ is the single smallest element, $A[2\mathinner{.\,.}n]$ is sorted, done.

Time. Line 1 is $O(n)$. Lines 3–5 are $O(\lg n)$ each (constant swap + Max-Heapify). Summing over $n-1$ iterations: $O(n) + (n-1)\cdot O(\lg n) = O(n \lg n)$. $\blacksquare$

Lower bound
The running time is actually $\Theta(n \lg n)$: the $\Omega(n \lg n)$ matching lower bound follows from the general comparison-sort lower bound, which we prove in §8.1.
Heapsort vs. other $\Theta(n \lg n)$ sorts
  • vs. Merge Sort. Heapsort is in-place; merge sort is not. Merge sort has better cache behaviour on large inputs and is stable; heapsort is not stable.
  • vs. Quicksort. Heapsort has a better worst case ($\Theta(n \lg n)$ vs. $\Theta(n^2)$). In practice, well-tuned quicksort is faster on most inputs because of cache effects and simpler inner loops — hence introsort (used in many C++ standard libraries) starts with quicksort and falls back to heapsort when the recursion depth exceeds $2 \lg n$.

Quicksort

Quicksort is the practical champion of in-memory sorting. Its worst case is poor ($\Theta(n^2)$), but in expectation on a random input — or, equivalently, when randomized — it runs in $\Theta(n \lg n)$ with small constants, and its inner loop is so cache-friendly that it outperforms heapsort on virtually every real input of moderate size. This chapter does three things: (i) presents quicksort and its Partition primitive; (ii) analyzes the worst and best cases; (iii) proves the randomized expected-time bound using indicator random variables — an application of Chapter 5's machinery to one of the most important algorithms in computer science.

7.1Description of Quicksort

Quicksort is divide-and-conquer. Given $A[p\mathinner{.\,.}r]$:

  1. Divide. Partition $A[p\mathinner{.\,.}r]$ into two (possibly empty) subarrays $A[p\mathinner{.\,.}q-1]$ and $A[q+1\mathinner{.\,.}r]$ such that every element of the first is $\le A[q]$ and every element of the second is $\ge A[q]$. Compute the index $q$ as part of this step.
  2. Conquer. Recursively sort $A[p\mathinner{.\,.}q-1]$ and $A[q+1\mathinner{.\,.}r]$.
  3. Combine. Nothing to do — the subarrays are already in place and globally sorted.
Quicksort vs. merge sort at a glance
Merge sort splits trivially (cut in half) and merges cleverly. Quicksort splits cleverly (partition around a pivot) and merges trivially (nothing to do — the parts are already in their final regions). Both are $\Theta(n \lg n)$ in the good case, but they bleed running time at different places: merge sort spends it in the combine step, quicksort spends it in partition. Quicksort's "combine is free" is why it's usually faster in practice — and why its worst case is worse (a bad pivot ruins the split).
Quicksort($A$, $p$, $r$)
1 if $p < r$ 2 $q$ = Partition($A$, $p$, $r$) 3 Quicksort($A$, $p$, $q-1$) 4 Quicksort($A$, $q+1$, $r$)

The heart of the algorithm is Partition. We describe the Lomuto scheme (CLRS's choice): use the last element $A[r]$ as the pivot, then in one left-to-right sweep, place everything $\le$ pivot to the left, everything $>$ pivot to the right, and swap the pivot into its final position.

The two-region walk

Picture the array as we sweep left-to-right with index $j$. We maintain two regions behind $j$: a "small stuff" region ending at $i$ (everything $\le$ pivot), and a "big stuff" region from $i+1$ to $j-1$ (everything $>$ pivot). The pivot itself sits at the far right, waiting.

<= pivot    > pivot    unscanned    pivot
[ ... | ... | ... | x ]
               i           j             r

Each step reads $A[j]$. If it's $>$ pivot, it joins the big-stuff region for free (just advance $j$). If it's $\le$ pivot, we grow the small-stuff region by one (advance $i$) and swap $A[i]$ with $A[j]$, which moves the small value to its slot and sends the big value it displaced to the back of the big-stuff region. At the end, one final swap puts the pivot between the regions. Everything is done in place in a single pass.

Partition($A$, $p$, $r$)
1 $x$ = $A[r]$ // pivot 2 $i$ = $p - 1$ 3 for $j = p$ to $r - 1$ 4 if $A[j] \le x$ 5 $i = i + 1$ 6 swap $A[i]$ with $A[j]$ 7 swap $A[i+1]$ with $A[r]$ 8 return $i + 1$
Theorem 7.1 (Partition correctness)
After Partition$(A, p, r)$ returns $q$, we have $p \le q \le r$ and:
  • $A[k] \le A[q]$ for $p \le k < q$,
  • $A[k] \ge A[q]$ for $q < k \le r$.
Proof (loop invariant)

Invariant. At the start of each iteration of the for-loop (line 3), for any array index $k$:

  1. If $p \le k \le i$, then $A[k] \le x$.
  2. If $i+1 \le k \le j-1$, then $A[k] > x$.
  3. If $k = r$, then $A[k] = x$.

Init. $i = p-1$ and $j = p$; the first two regions are empty; the third holds by line 1.

Maintenance. Two cases on $A[j]$. If $A[j] > x$: increment $j$ only; the new element joins the "$> x$" region (b). If $A[j] \le x$: increment $i$, then swap $A[i]$ with $A[j]$. The element that was at $A[j]$ (which is $\le x$) moves to position $i$, extending (a); the element that was at $A[i]$ — which by (b) was $> x$ — moves to position $j$ and is about to leave the scan; incrementing $j$ extends (b) with this displaced element.

Termination. At $j = r$: (a) gives $A[p\mathinner{.\,.}i] \le x$, (b) gives $A[i+1\mathinner{.\,.}r-1] > x$, and (c) gives $A[r] = x$. The swap on line 7 places $x$ at position $i+1$; the subarray $A[p\mathinner{.\,.}i]$ is unchanged (all $\le x$) and $A[i+2\mathinner{.\,.}r]$ holds the values that were $> x$ (shuffled, but all still $> x$). The return value $q = i+1$ satisfies the claim. $\blacksquare$

Partition runs in $\Theta(r - p + 1)$
The for-loop runs $r - p$ times; each iteration does $O(1)$ work. Hence partitioning a subarray of length $n$ takes $\Theta(n)$.

7.2Performance of Quicksort

The running time of Quicksort depends on the balance of each partition — whether the pivot splits the subarray roughly in half, or lands at one end. Two extremes bracket the analysis.

Why balance is everything

Each partition does $\Theta(n)$ work. If the recursion tree has depth $d$, every level must do somewhere between $0$ and $n$ units of work, and the total work is bounded by $O(nd)$. So the whole question is: how deep does the tree get?

If the pivot always hits the middle, the tree is perfectly balanced, depth $\lg n$, total $\Theta(n \lg n)$. If the pivot always hits an end, the tree degenerates into a long chain, depth $n$, total $\Theta(n^2)$. Reality sits somewhere in between, and the next several sections are about characterizing where.

Theorem 7.2 (Worst-case running time)
The worst-case running time of Quicksort is $\Theta(n^2)$, achieved when the input is already sorted (ascending or descending).
Proof

If every partition is maximally unbalanced — one side of size $n-1$, the other empty — the recurrence is $T(n) = T(n-1) + T(0) + \Theta(n) = T(n-1) + \Theta(n)$. Expanding: $T(n) = \Theta(n) + \Theta(n-1) + \cdots + \Theta(1) = \Theta(n^2)$.

On an already-sorted input, Lomuto partition with $A[r]$ as pivot always places it last (the max), giving one empty side and one full side of size $n-1$. This realizes the worst case.

One can prove by substitution that $T(n) = O(n^2)$ holds for any split pattern (the worst case is indeed the worst), so $\Theta(n^2)$ is tight. $\blacksquare$

The irony of sorted input
A sorted array is in some sense the best possible input — already sorted — and yet Lomuto quicksort chokes on it worst of all. The reason: Lomuto picks the last element as pivot, which on a sorted input is always the maximum. Every split peels off a single max and recurses on everything else. This is the degenerate chain recurrence. The same happens in reverse on a descending input. Randomization (§7.3) precisely breaks this correlation between input structure and pivot choice.
Theorem 7.3 (Best case)
If every partition is exactly balanced — both sides of size $\lfloor n/2 \rfloor$ or $\lceil n/2 \rceil - 1$ — then $T(n) = \Theta(n \lg n)$.
Proof
$T(n) \le 2T(n/2) + \Theta(n)$, which by the master theorem Case 2 is $\Theta(n \lg n)$. $\blacksquare$
The surprising truth about balance

One might worry that quicksort needs nearly-perfect balance to achieve $O(n \lg n)$ — but it doesn't. Any constant-factor balance suffices. If every partition produces a split of, say, $1:99$ (one side gets $n/100$, the other gets $99n/100$), the recurrence is $T(n) = T(n/100) + T(99n/100) + cn$. The recursion tree has depth $\log_{100/99} n = \Theta(\lg n)$, and every level does $\Theta(n)$ work, yielding $T(n) = \Theta(n \lg n)$. Only partitions where one side is $\Omega(n - o(n))$ produce superlogarithmic depth.

Why a "constant-fraction" split is good enough

Here's a cute way to see it. Imagine a partition where the smaller side has $\alpha n$ elements for some $0 < \alpha \le 1/2$. The subproblem sizes at depth $d$ are (at most) $(1-\alpha)^d n$. We stop when the size drops below $1$, so $(1-\alpha)^d n \le 1$, giving $d \le \log_{1/(1-\alpha)} n = \Theta(\lg n)$ for any fixed $\alpha > 0$.

The deep point: the recursion tree doesn't care whether $\alpha$ is $1/2$ or $1/1000$ — it just needs $\alpha$ to be bounded away from $0$. A $1:1000$ split is asymptotically as good as $1:1$. This is why randomization works so well: we don't need great pivots, just not terrible ones, and most random pivots aren't terrible.

Average case (intuition, made rigorous in §7.4)
Imagine the algorithm alternates a $0:(n-1)$ split with a $(n/2-1):(n/2-1)$ split at every recursion level. The "wasted" unbalanced level does only $\Theta(n)$ work, and the balanced level immediately cuts the problem in half. The tree has depth $\Theta(\lg n)$ and total work $\Theta(n \lg n)$ — the same asymptotics as the best case. This suggests that most splits don't need to be good; only enough of them.

7.3A Randomized Version of Quicksort

Since the algorithm's fate hinges on pivot quality, and an adversary can always construct a worst-case input for a deterministic pivot choice, we randomize the pivot. The simplest change: pick the pivot uniformly at random from $A[p\mathinner{.\,.}r]$ before partitioning.

Randomized-Partition($A$, $p$, $r$)
1 $i$ = Random($p$, $r$) 2 swap $A[r]$ with $A[i]$ 3 return Partition($A$, $p$, $r$)
Randomized-Quicksort($A$, $p$, $r$)
1 if $p < r$ 2 $q$ = Randomized-Partition($A$, $p$, $r$) 3 Randomized-Quicksort($A$, $p$, $q-1$) 4 Randomized-Quicksort($A$, $q+1$, $r$)

This is a Las Vegas algorithm: the answer is always correct; only the running time is random. Crucially, on any input, the distribution of running times is the same — an adversary gains nothing by choosing a particular input, because they cannot predict our coin flips.

Equivalence with probabilistic analysis
An alternative view: running Randomized-Quicksort on a fixed input is statistically identical to running deterministic Quicksort on a uniformly random permutation of that input. Both generate the same distribution over comparison sequences. This equivalence lets us analyze one by analyzing the other.

7.4Analysis of Quicksort

We now prove the headline result: randomized quicksort runs in $O(n \lg n)$ expected time on any input. The argument is one of the classic applications of indicator random variables, and it is worth working through slowly.

The strategy, before we dive in

It's tempting to set up the recurrence $\operatorname{E}[T(n)] = (\text{average over pivot choices})$ and slog through. That works but is tedious. CLRS uses a slicker approach: count comparisons directly.

Here's the trick. The running time of quicksort is proportional to the total number of comparisons performed — so let $X$ = total comparisons, and show $\operatorname{E}[X] = O(n \lg n)$. To get $X$, we don't track which comparisons happen when. Instead, for every pair of elements $(z_i, z_j)$, we ask: over the whole algorithm's run, does this pair ever get compared? That's a 0/1 question — an indicator variable. Sum those indicators over all pairs and you have $X$.

The reason this works: any two elements are compared at most once. Once one of them becomes a pivot, it's placed and never looked at again; if neither is a pivot, their pair only gets compared when one is eventually picked as pivot. So the indicator-per-pair framing is exact, not approximate.

This converts a complicated timing question into $\binom{n}{2}$ independent probability calculations, each solvable by a single symmetry argument. Everything else is bookkeeping.

Theorem 7.4 (Expected time of randomized quicksort)
The expected running time of Randomized-Quicksort on an input of $n$ distinct elements is $O(n \lg n)$.
Proof

The running time is dominated by the total number of comparisons made by Partition across the entire recursion. Let $X$ be this total. We show $\operatorname{E}[X] = O(n \lg n)$, from which $O(n \lg n)$ expected total work follows.

Rename the elements of $A$ to be $z_1 < z_2 < \cdots < z_n$ in sorted order. For $1 \le i < j \le n$, let $$X_{ij} = I\{z_i \text{ is compared to } z_j \text{ at some point during the algorithm}\}.$$ Every comparison in Partition is between the current pivot and some other element in the subarray. Any two elements are compared at most once (once an element is a pivot, it is placed into its final position and never compared again). Hence the total number of comparisons is $$X = \sum_{i=1}^{n-1} \sum_{j=i+1}^{n} X_{ij}.$$

By linearity of expectation, $$\operatorname{E}[X] = \sum_{i < j} \Pr[X_{ij} = 1].$$

Key combinatorial lemma. Elements $z_i$ and $z_j$ are compared iff either $z_i$ or $z_j$ is the first pivot chosen from the set $Z_{ij} = \{z_i, z_{i+1}, \ldots, z_j\}$.

Why: Walk down the recursion. Initially $Z_{ij}$ is entirely in the same subarray. It remains so until a pivot falls inside $Z_{ij}$. If that pivot is $z_i$ or $z_j$, it is compared to the other. Otherwise (the pivot is some $z_k$ with $i < k < j$), the split separates $z_i$ into the left subarray and $z_j$ into the right — they will never share a subarray again, and hence never be compared.

Computing $\Pr[X_{ij} = 1]$. By symmetry, each element of $Z_{ij}$ is equally likely to be the first pivot chosen from $Z_{ij}$. The set has $j - i + 1$ elements and two of them trigger a comparison ($z_i$ or $z_j$), so $$\Pr[X_{ij} = 1] = \frac{2}{j - i + 1}.$$

Putting it together. $$\operatorname{E}[X] = \sum_{i=1}^{n-1}\sum_{j=i+1}^{n} \frac{2}{j-i+1} = \sum_{i=1}^{n-1}\sum_{k=1}^{n-i} \frac{2}{k+1} < \sum_{i=1}^{n-1} 2 H_n = O(n \lg n).$$ We used $H_n = \sum_{k=1}^n 1/k = \Theta(\lg n)$. Since each comparison corresponds to $O(1)$ work, the total expected running time is $O(n \lg n)$. $\blacksquare$

The lemma, unpacked

The key combinatorial lemma is the subtle step, so let's draw it. Imagine the $n$ elements arranged in sorted order on a line, and highlight $z_i$ and $z_j$:

• • • | zi  •  •  •  zj | • • •

The bullets between $z_i$ and $z_j$ are the strict interior of $Z_{ij}$. Quicksort processes subarrays top-down, picking pivots one at a time. There are three fates for $z_i$ and $z_j$:

  1. $z_i$ is the first $Z_{ij}$ element picked as pivot. Partitioning with $z_i$ compares it against every other element still in the subarray — including $z_j$. So $X_{ij} = 1$.
  2. $z_j$ is first. Symmetric to case 1. $X_{ij} = 1$.
  3. Some interior $z_k$ ($i < k < j$) is first. The partition splits everything smaller to the left and larger to the right. $z_i$ goes left; $z_j$ goes right. They now live in different subarrays forever. They can never be compared.

So $X_{ij} = 1$ exactly when the first pivot in $Z_{ij}$ is one of the two endpoints — 2 favorable cases out of $|Z_{ij}| = j - i + 1$ equally likely possibilities.

Where the $\ln n$ comes from, one more way

After the dust settles we see that on average, each element is compared to $2H_n - O(1) \approx 2\ln n$ others. There are $n$ elements, so the total comparison count is $\approx n \ln n$. That's heuristic but true.

Intuition: a given element $z_i$ is compared to $z_j$ with probability $2/(|i-j|+1)$. Distance-1 neighbors are compared with probability $1$; distance-2 neighbors with $2/3$; and far-apart elements with probability decaying like $1/|i-j|$. Summing over all $j$ gives a harmonic series — $\Theta(\ln n)$ — which is why the total is $\Theta(n \ln n)$ and not, say, $\Theta(n^2)$. The distant pairs are almost never compared; quicksort's partitioning decisions efficiently separate them after a few top-level splits.

What makes this proof work
Notice how little probabilistic machinery we actually used: indicator variables, linearity, and one symmetry argument. We did not reason about the joint distribution of comparisons, the structure of the recursion tree on a random input, or any complicated conditioning. This is a model-example of how powerful indicator RVs are.

Chapter 8

Sorting in Linear Time

All the sorts seen so far — insertion, merge, heap, quick — are comparison sorts. They determine the sorted order solely by pairwise comparisons of input elements. We now prove a fundamental lower bound: any comparison sort, however clever, requires $\Omega(n \lg n)$ comparisons in the worst case. Then we exhibit three algorithms that beat this bound by not being comparison sorts — they exploit structural properties of the input (small integer range; fixed number of digits; uniform distribution) to achieve linear expected or worst-case time.

8.1Lower Bounds for Sorting

The big question of this chapter
Chapters 2–7 built a menu of $\Theta(n \lg n)$ sorts. Is that the best we can do? Can someone, ever, find a sort that runs in $\Theta(n)$? The answer is: not by comparisons alone — which is what this section proves. But if we let the algorithm look at the bits of each element (not just compare them), we can do better. The rest of Chapter 8 exhibits three such algorithms.
The comparison model & decision trees
A comparison sort is an algorithm whose only access to input elements is through pairwise tests $A[i] \lessgtr A[j]$. Any such algorithm, run on inputs of a fixed length $n$, can be represented by a decision tree: an internal node is a comparison, its two children are the branches taken on $\le$ vs. $>$, and each leaf is labeled with the permutation $\pi$ such that "the sorted order is $A[\pi(1)] \le A[\pi(2)] \le \cdots \le A[\pi(n)]$".
What the decision tree represents

Fix $n$ and fix the algorithm. Run it on every possible input. At each step the algorithm makes some comparison $A[i] : A[j]$ and branches on $\le$ or $>$. So the entire execution tree is a binary tree whose internal nodes are "which comparison gets asked?" and whose leaves are "which permutation does the algorithm declare sorted?"

For the algorithm to be correct, every distinct input ordering must reach a different leaf — if two different input orderings both ended at the same leaf, the algorithm would produce the same output for both, and it would be wrong on at least one.

There are $n!$ possible input orderings, so the tree has at least $n!$ leaves. A binary tree with $\ell$ leaves has height $\ge \lceil \lg \ell \rceil$. That's the entire argument — everything else is estimating $\lg(n!)$.

Tiny example: $n = 3$

For three elements $a_1, a_2, a_3$ there are $3! = 6$ possible orderings. Any correct comparison sort on three elements has a decision tree with $\ge 6$ leaves, so its height must be $\ge \lceil \lg 6 \rceil = 3$. Insertion sort on three elements does make $3$ comparisons in the worst case — so it is optimal at $n = 3$.

At $n = 4$: $4! = 24$ leaves, height $\ge \lceil \lg 24 \rceil = 5$. At $n = 5$: $5! = 120$, height $\ge 7$. In general $\lg(n!) \approx n \lg n - 1.443 n$, which is where the $\Omega(n \lg n)$ bound comes from.

Theorem 8.1 (Lower bound for comparison sorts)
Any comparison sort requires $\Omega(n \lg n)$ comparisons in the worst case. More precisely, the height of any decision tree that sorts $n$ elements is $\ge \lceil \lg(n!) \rceil = n \lg n - n \lg e + \Theta(\lg n) = \Omega(n \lg n)$.
Proof

Let $T$ be the decision tree of a correct comparison sort on inputs of size $n$, and let $h$ be its height. Correctness requires that every of the $n!$ possible orderings of the input corresponds to some root-to-leaf path in $T$ — otherwise there is some permutation the algorithm fails to sort correctly. Hence $T$ has at least $n!$ leaves.

A binary tree of height $h$ has at most $2^h$ leaves. Therefore $$2^h \ge n! \quad\Longrightarrow\quad h \ge \lg(n!).$$

By Stirling's approximation (§3.2), $$\lg(n!) = \lg\!\left(\sqrt{2\pi n} \cdot \left(\frac{n}{e}\right)^n \cdot (1 + O(1/n))\right) = n \lg n - n \lg e + \tfrac{1}{2}\lg n + \Theta(1) = \Omega(n \lg n).$$ $\blacksquare$

Corollary — optimality of merge sort & heapsort
Merge sort and heapsort both make $O(n \lg n)$ comparisons in the worst case. By Theorem 8.1 this is optimal up to constants — no comparison sort can do asymptotically better.

8.2Counting Sort

Counting sort sorts an array $A$ of $n$ integers each in the range $\{0, 1, \ldots, k\}$. It runs in $\Theta(n + k)$ time — linear in $n$ when $k = O(n)$. No comparisons are performed; instead, we count how many elements are $\le$ each value.

The three-pass plan

Counting sort is just three passes over the data:

  1. Tally: for each value $v \in \{0, \ldots, k\}$, count how many times it appears in $A$. Store in $C[v]$.
  2. Prefix sum: turn $C[v]$ into "number of elements $\le v$" by running $C[v] \mathrel{+}= C[v-1]$ from left to right. Now $C[v]$ is the final position where the last copy of $v$ should land in sorted order.
  3. Scatter: walk $A$ right to left. For each $A[j]$, read its rank $r = C[A[j]]$, place $A[j]$ at $B[r]$, and decrement $C[A[j]]$ so the next copy goes one slot earlier.

The key insight is Pass 2. Once we know how many elements are $\le v$ for every $v$, we know exactly where to put each element — no comparisons, no searching. The prefix sum converts "count of each value" into "where each value goes."

Why walk $A$ right to left in Pass 3? So that equal elements preserve their input order (the rightmost copy of $v$ goes to the highest slot, the leftmost goes earliest). That's stability — essential for radix sort (§8.3).

Counting-Sort($A$, $B$, $k$)
1 let $C[0\mathinner{.\,.}k]$ be a new array 2 for $i = 0$ to $k$: $C[i] = 0$ 3 for $j = 1$ to $A$.length: $C[A[j]] = C[A[j]] + 1$ // $C[i]$ = count of $i$ 4 for $i = 1$ to $k$: $C[i] = C[i] + C[i-1]$ // $C[i]$ = # elements $\le i$ 5 for $j = A$.length downto $1$ 6 $B[C[A[j]]] = A[j]$ 7 $C[A[j]] = C[A[j]] - 1$
Theorem 8.2 (Counting sort correctness & complexity)
Counting-Sort produces $B$ as a sorted permutation of $A$, runs in $\Theta(n + k)$ time, and is stable: equal elements appear in $B$ in the same order as in $A$.
Proof of correctness

After line 4, $C[i]$ equals the number of elements of $A$ with value $\le i$. Hence if there are $c$ elements with value equal to some specific $v$, they should occupy positions $C[v-1]+1, C[v-1]+2, \ldots, C[v]$ in the sorted output.

The descending loop at lines 5–7 processes each $A[j]$ and writes it to position $C[A[j]]$, then decrements. After placing the first occurrence of value $v$ encountered in the descending scan, $C[v]$ drops by 1, so the next occurrence (from the left) is placed one slot earlier. Since we process $A$ from right to left, the rightmost occurrence lands in the highest slot — preserving input order among equals. Stability is therefore a consequence of iterating line 5 from high $j$ to low.

Time: Lines 2 and 4 are $\Theta(k)$; lines 3 and 5–7 are $\Theta(n)$. Total: $\Theta(n + k)$. $\blacksquare$

When counting sort wins
When $k = O(n)$, total time is $\Theta(n)$ — beating the $\Omega(n \lg n)$ comparison-sort lower bound. When $k = \omega(n)$, counting sort is worse than merge sort. Counting sort shines on small-range integer keys (ages, flags, pixel values).

8.3Radix Sort

Radix sort sorts a list of $n$ integers (or fixed-length strings) each of $d$ digits, where each digit is in the range $\{0, 1, \ldots, k-1\}$. The algorithm sorts by each digit in turn, starting from the least significant digit. The auxiliary sort on each digit must be stable — typically counting sort.

Why least-significant first is the clever move

When you're told "sort by digit-1, then digit-2, then digit-3," you probably think "most significant first, then break ties with the next digit, and so on." That works, but forces you to track sub-groups and re-sort within each — it's recursive.

LSD radix sort does the opposite and avoids all that bookkeeping. The trick: each pass re-sorts the entire array on one digit, with a stable sort. After the last (most significant) pass, the array is globally sorted.

Why? Because stability preserves the previous pass's work. After sorting on the least-significant digit, the array is sorted by that digit. On the next pass we sort by the next digit up — and whenever two elements tie on the new digit, stability keeps them in the order they had from the earlier pass, which is exactly the tiebreaker we want ("earlier digit wins only if later digits tie"). Induct.

LSD radix sort on a worked example

Sort $[329, 457, 657, 839, 436, 720, 355]$ by digit, base 10.

Input:        329  457  657  839  436  720  355
After ones:   720  355  436  457  657  329  839
After tens:   720  329  436  839  355  457  657
After hundreds: 329  355  436  457  657  720  839

Look at the tens pass. It placed $720$ first because it has tens-digit $2$. But $329$ and $839$ both have tens-digit $3$. They keep their order from the previous (ones-digit) pass: $329$ came before $839$ there, and still does. That's stability doing the work.

Radix-Sort($A$, $d$)
1 for $i = 1$ to $d$ 2 use a stable sort (e.g. counting sort) to sort $A$ on digit $i$
Theorem 8.3 (Radix sort correctness)
Given $n$ $d$-digit numbers in base $k$, Radix-Sort sorts them in $\Theta(d(n+k))$ time.
Proof of correctness

By induction on $i$: after the $i$-th stable pass, the array is sorted according to the low-order $i$ digits.

Base ($i = 1$): direct.

Step ($i > 1$): assume sortedness on low-order $(i-1)$ digits. The $i$-th pass performs a stable sort on digit $i$. Consider two elements $x, y$. If they differ in digit $i$, the stable sort places them in the correct order with respect to digit $i$, which (by definition of the ordering on numbers) is the correct order. If they agree in digit $i$, stability preserves their previous order — which by the inductive hypothesis matches their ordering on the low-order $(i-1)$ digits, precisely the right tiebreaker. $\blacksquare$

Why LSD and not MSD?
Most-significant-digit-first (MSD) radix sort is possible, but requires dividing the array into groups (by the current digit) and recursing on each group — adding complexity and destroying in-place behaviour. LSD is the simpler, flat version.
Example 8.1 — Choosing the base

To sort $n$ numbers each with $b$ bits, we can view each number as having $d = \lceil b/r \rceil$ digits in base $k = 2^r$. Each counting-sort pass takes $\Theta(n + 2^r)$, so total time is $\Theta((b/r)(n + 2^r))$.

For $b \le \lg n$, choosing $r = b$ gives $\Theta(n + 2^b) = \Theta(n)$ (one pass). For larger $b$, the optimal $r$ is approximately $\lg n$, giving total time $\Theta(bn / \lg n)$. So radix sort's advantage over merge sort depends strongly on how many bits the keys have.

8.4Bucket Sort

Bucket sort assumes the input is drawn uniformly at random from $[0, 1)$. Divide $[0, 1)$ into $n$ equal-size buckets and scatter the inputs into them. Each bucket holds, in expectation, $1$ element. Sort each bucket (with insertion sort, say) and concatenate.

The pigeonhole vs. the average

If $n$ balls fall independently and uniformly into $n$ bins, how many land in each bin? On average, $1$ — but not all buckets get exactly one. Some will get $0$ (missed), some will get $2$ or $3$ or more (collisions). The distribution is Poisson-like.

The catch: when a bucket gets $n_i$ elements, insertion-sorting that bucket costs $\Theta(n_i^2)$, not $\Theta(n_i)$. So if one bucket got unlucky and received, say, all $n$ elements, we'd pay $\Theta(n^2)$ — ruining the whole scheme.

The miracle is that on average this doesn't happen. The expected value of $\sum n_i^2$ is $\Theta(n)$, not $\Theta(n^2)$. That's what we need to prove, and the proof is just indicator random variables again — same technique, fresh application.

Bucket-Sort($A$)
1 $n$ = $A$.length 2 let $B[0\mathinner{.\,.}n-1]$ be a new array of empty lists 3 for $i = 1$ to $n$ 4 append $A[i]$ to list $B[\lfloor n \cdot A[i] \rfloor]$ 5 for $i = 0$ to $n - 1$ 6 sort list $B[i]$ with insertion sort 7 concatenate $B[0], B[1], \ldots, B[n-1]$
Theorem 8.4 (Expected time)
Under the uniform-distribution assumption, Bucket-Sort runs in $\Theta(n)$ expected time.
Why the $n_i^2$ trick works out to $\Theta(n)$

The suspicious move in the analysis is replacing "$\sum n_i^2$" (which looks like it could blow up to $n^2$) with its expectation. Here's the key number: $\operatorname{E}[n_i^2] = 2 - 1/n \approx 2$, independent of $n$.

Think of each bucket in isolation. Each of the $n$ elements goes into bucket $i$ with probability $1/n$; the expected count is $1$. The variance turns out to be almost $1$ as well ($1 - 1/n$), so $\operatorname{E}[n_i^2] = \operatorname{Var}(n_i) + \operatorname{E}[n_i]^2 = (1 - 1/n) + 1 = 2 - 1/n$. Roughly: "expected count squared" is $2$, not $n$.

Summing over $n$ buckets: $\operatorname{E}[\sum n_i^2] = n \cdot (2 - 1/n) \approx 2n$. So the total quadratic-in-bucket-size work is linear. Insertion sort is slow per bucket (in worst case) but buckets are tiny in expectation, and the small constants beat merge-sort overhead.

Proof

Lines 1–4 and 7 together take $\Theta(n)$ deterministically. The randomness lives in line 6. Let $n_i$ be the number of elements landing in bucket $i$. Insertion sort on $n_i$ elements is $O(n_i^2)$, so the total cost of line 6 is $\sum_{i=0}^{n-1} O(n_i^2)$.

We compute $\operatorname{E}[n_i^2]$. For each $j$, let $X_{ij} = I\{A[j] \text{ falls into bucket } i\}$. Then $n_i = \sum_j X_{ij}$ and $$\operatorname{E}[n_i^2] = \operatorname{E}\!\left[\left(\sum_j X_{ij}\right)^{\!2}\right] = \sum_{j=1}^{n} \operatorname{E}[X_{ij}^2] + \sum_{j \ne k} \operatorname{E}[X_{ij} X_{ik}].$$ Since $X_{ij}$ is 0/1, $X_{ij}^2 = X_{ij}$, so $\operatorname{E}[X_{ij}^2] = 1/n$. For $j \ne k$, the indicators are independent (uniform distribution), so $\operatorname{E}[X_{ij} X_{ik}] = (1/n)^2 = 1/n^2$. Hence $$\operatorname{E}[n_i^2] = n \cdot \tfrac{1}{n} + n(n-1) \cdot \tfrac{1}{n^2} = 1 + 1 - \tfrac{1}{n} = 2 - \tfrac{1}{n}.$$ Summing over $n$ buckets: $\operatorname{E}[\sum n_i^2] = n(2 - 1/n) = \Theta(n)$. $\blacksquare$

What if the input isn't uniform?
The expected-time bound depends on the uniformity assumption; for adversarial input (e.g. all elements in bucket 0) bucket sort degrades to $\Theta(n^2)$. If the input distribution is known to be something else, one can adapt the bucket boundaries (non-equal partitioning) to re-establish the expected-$O(1)$-per-bucket property.

Chapter 9

Medians & Order Statistics

Chapter 8 closed the book on sorting: $\Theta(n \lg n)$ in the comparison model, $\Theta(n)$ when extra structure is available. This chapter asks a thinner question. Instead of the whole sorted order, what if we only want the $i$-th smallest element — the median, say, or the maximum? We could sort and index into the result for $\Theta(n \lg n)$, but that wastes effort: we are computing $n - 1$ ranks we don't care about. The deeper claim of this chapter is that selection is intrinsically easier than sorting: it can be done in $\Theta(n)$ time. We give two proofs — a randomized algorithm with expected linear time (§9.2), and a remarkable deterministic algorithm with worst-case linear time (§9.3).

The selection problem
Input. A set $A$ of $n$ distinct numbers and an integer $i$ with $1 \le i \le n$.
Output. The element $x \in A$ that is larger than exactly $i - 1$ other elements of $A$. We call $x$ the $i$-th order statistic.
Vocabulary
The minimum is the $1$st order statistic; the maximum is the $n$-th. The median is the "middle" element — the lower median is the $\lceil n/2 \rceil$-th order statistic, the upper median is the $\lfloor n/2 \rfloor + 1$-th. When $n$ is odd they coincide; when $n$ is even the term median in CLRS refers to the lower median by convention.

9.1Minimum and Maximum

How many comparisons does it take to find the minimum of $n$ elements? The obvious algorithm sweeps through, keeping the smallest seen so far:

Minimum($A$)
1 $\textit{min}$ = $A[1]$ 2 for $i = 2$ to $A$.length 3 if $\textit{min} > A[i]$ 4 $\textit{min}$ = $A[i]$ 5 return $\textit{min}$

This makes exactly $n - 1$ comparisons. Can we do fewer? No — and the reason is delightfully clean.

A tournament argument

Think of the $n$ elements as players in a tournament. A comparison is a match: the loser is "eliminated" from contention for the title of minimum. To declare a single winner, we must have eliminated all $n - 1$ other players. Each match eliminates exactly one player. Hence at least $n - 1$ matches are required.

This is a lower bound: any algorithm for the minimum — clever or naive, deterministic or randomized — must perform $\ge n - 1$ comparisons in the worst case. The simple sweep above matches it.

Theorem 9.1 (Optimality of the simple minimum)
Finding the minimum of $n$ distinct elements requires exactly $n - 1$ comparisons in the worst case. The algorithm Minimum is optimal.

Simultaneous Minimum and Maximum

A more interesting question: how many comparisons to find both the minimum and the maximum? The naive approach — run Minimum and then Maximum independently — uses $2(n - 1) = 2n - 2$ comparisons. We can do better.

Process elements in pairs

Here is the trick. Compare the elements two at a time. For each pair $(a, b)$, the smaller one is a candidate for minimum and the larger one a candidate for maximum — but the two never compete with each other again. So one comparison per pair sorts the pair; then we update the running min using only the pair-loser and the running max using only the pair-winner.

That's $3$ comparisons per pair: $1$ to compare the pair, then $1$ each to update min and max. Compared to the naive $4$ comparisons per pair (each element compared against both running min and running max), we save $25\%$.

Theorem 9.2 (Min and max in $3 \lfloor n/2 \rfloor$ comparisons)
We can find both the minimum and the maximum of $n$ distinct elements using at most $3 \lfloor n/2 \rfloor$ comparisons.
Proof & algorithm

Initialization. If $n$ is odd, set $\textit{min} = \textit{max} = A[1]$ and start the pair-processing at index $2$. If $n$ is even, compare $A[1]$ with $A[2]$ ($1$ comparison) and set $\textit{min}$ to the smaller, $\textit{max}$ to the larger; start pair-processing at index $3$.

Main loop. For each remaining pair $(A[i], A[i+1])$:

  1. Compare $A[i]$ with $A[i+1]$ ($1$ comparison). Call the smaller $s$ and the larger $\ell$.
  2. Compare $s$ with $\textit{min}$; update if smaller ($1$ comparison).
  3. Compare $\ell$ with $\textit{max}$; update if larger ($1$ comparison).

Comparison count. If $n$ is even, the initial pair costs $1$, then we process $(n-2)/2$ more pairs at $3$ each: total $1 + 3(n-2)/2 = (3n - 4)/2 = 3n/2 - 2 \le 3 \lfloor n/2 \rfloor$. If $n$ is odd, no initial cost, and we process $(n-1)/2$ pairs at $3$ each: total $3(n-1)/2 = 3 \lfloor n/2 \rfloor$. $\blacksquare$

A factor of $4/3$, not $2$
Naive: $\sim 2n$. Pair-processing: $\sim 3n/2$. Ratio: $4/3$. The savings come from refusing to compare a pair-loser against the running max (it cannot be the max — it lost a comparison) or a pair-winner against the running min. Information already extracted from one comparison is reused.

9.2Selection in Expected Linear Time

For arbitrary $i$ — not just $1$ or $n$ — we need a different idea. The key observation: Partition from §7.1 is a selection primitive in disguise. After partitioning $A[p\mathinner{.\,.}r]$ around a pivot, the pivot lands at some position $q$. The pivot is then the $(q - p + 1)$-th smallest in the subarray. Whichever side of the partition contains the rank we want, we can recurse on only that side — ignoring the other.

Why one-sided recursion changes everything

Quicksort recurses on both halves of every partition; the work doubles each level on average, balanced against halving subproblem size. The recurrence is $T(n) = 2T(n/2) + \Theta(n)$, which by master theorem Case 2 gives $\Theta(n \lg n)$.

Selection only needs one half. The recurrence becomes $T(n) = T(\alpha n) + \Theta(n)$ for some fraction $\alpha < 1$. By master theorem Case 3 (or just summing a geometric series: $n + \alpha n + \alpha^2 n + \cdots = n / (1 - \alpha)$), this is $\Theta(n)$.

The whole question becomes: can we keep $\alpha$ bounded away from $1$? A pivot that always splits off only one element gives $\alpha \approx 1$, recurrence $T(n) = T(n-1) + \Theta(n)$, total $\Theta(n^2)$. A pivot that splits in half gives $\alpha = 1/2$, total $\Theta(n)$. As with quicksort, we need any constant fraction away from the extremes — randomization (this section) or the median-of-medians construction (next section) provides it.

Randomized-Select($A$, $p$, $r$, $i$)
1 if $p == r$ 2 return $A[p]$ 3 $q$ = Randomized-Partition($A$, $p$, $r$) 4 $k$ = $q - p + 1$ // rank of pivot within $A[p\mathinner{.\,.}r]$ 5 if $i == k$ 6 return $A[q]$ // pivot is the answer 7 elseif $i < k$ 8 return Randomized-Select($A$, $p$, $q-1$, $i$) 9 else 10 return Randomized-Select($A$, $q+1$, $r$, $i - k$)

Note line 10: when we recurse on the right side, we must adjust the rank we're looking for. The right subarray $A[q+1\mathinner{.\,.}r]$ contains the elements ranked $k+1, k+2, \ldots$ in the current subarray; the element of rank $i$ in $A[p\mathinner{.\,.}r]$ is the element of rank $i - k$ within $A[q+1\mathinner{.\,.}r]$.

Worst-Case and Expected Analysis

Theorem 9.3 (Worst case)
The worst-case running time of Randomized-Select is $\Theta(n^2)$.
Proof
If by bad luck the pivot is the maximum (or minimum) at every recursive call, and we are looking for an order statistic at the opposite end, the recurrence is $T(n) = T(n-1) + \Theta(n) = \Theta(n^2)$. This requires a sequence of $n$ unfortunate independent coin flips and so has probability $1/n!$ — vanishingly small — but it is possible. $\blacksquare$
Theorem 9.4 (Expected linear time)
On any input of $n$ distinct elements, Randomized-Select runs in $O(n)$ expected time.
Two ways to see why this is $O(n)$

Geometric expansion. Suppose the random pivot's rank is uniform on $\{1, \ldots, n\}$. Then with probability at least $1/2$ the pivot lies in the middle half — that is, in positions $n/4$ through $3n/4$. Whichever side of such a pivot we recurse on has size at most $3n/4$. So on average, every two recursive calls shrink the subproblem by a factor of $3/4$ or better. Plug into the geometric sum: total expected work is $\le n + \tfrac{3}{4}n + (\tfrac{3}{4})^2 n + \cdots = 4n = O(n)$.

Indicator variables. The full proof uses the same technology as quicksort's analysis (§7.4): write the running time as a sum of comparison indicators, exploit symmetry to compute each $\Pr$, sum, and bound. The structure of the sum changes because we recurse on only one side — that's where the savings come from.

Proof of Theorem 9.4

Let $T(n)$ be the expected running time of Randomized-Select on a subarray of size $n$. The pivot's rank within $A[p\mathinner{.\,.}r]$ is uniform on $\{1, 2, \ldots, n\}$ (this is the point of randomization). When the pivot has rank $k$, the algorithm either returns immediately ($i = k$, costing $\Theta(n)$ for the partition), recurses on the left subarray of size $k - 1$ (if $i < k$), or recurses on the right subarray of size $n - k$ (if $i > k$). In every case, the recursive call is on a subarray of size at most $\max(k - 1, n - k)$.

To get a clean upper bound that does not depend on $i$, define $$U(n) = \frac{1}{n} \sum_{k=1}^{n} T(\max(k - 1, n - k)).$$ By case-splitting on $k$, the values $\max(k-1, n-k)$ for $k = 1, \ldots, n$ run through $\lfloor n/2 \rfloor, \lfloor n/2 \rfloor + 1, \ldots, n-1$ each appearing at most twice. Hence $$T(n) \le \frac{2}{n} \sum_{k = \lfloor n/2 \rfloor}^{n-1} T(k) + O(n).$$

Substitution. We claim $T(n) \le c n$ for some constant $c > 0$ and all sufficiently large $n$. Plugging in, $$T(n) \le \frac{2c}{n} \sum_{k = \lfloor n/2 \rfloor}^{n-1} k + O(n) \le \frac{2c}{n} \cdot \frac{1}{2}\left((n-1) + \tfrac{n}{2}\right)\left((n - 1) - \tfrac{n}{2} + 1\right) + O(n).$$ Expanding the product and simplifying (CLRS does this as an exercise; the answer is the same to leading order): $$T(n) \le \frac{2c}{n} \cdot \frac{3n^2/8 + O(n)}{1} + O(n) = \frac{3cn}{4} + O(n).$$ Choose $c$ large enough that the $O(n)$ term is $\le c n / 4$. Then $T(n) \le 3cn/4 + cn/4 = cn$. The induction goes through, so $T(n) = O(n)$. $\blacksquare$

The constant matters
The proof gives a bound of roughly $4n$ to $8n$ comparisons in expectation, depending on bookkeeping. This is competitive with sorting-based approaches even at small $n$, and dominates them for $n \gtrsim 100$. In practice, Randomized-Select is the algorithm to reach for — the worst-case linear-time variant of §9.3 has larger hidden constants and is rarely used.

9.3Selection in Worst-Case Linear Time

The randomized algorithm is $\Theta(n)$ in expectation, but its worst case is still $\Theta(n^2)$. Can we eliminate the bad luck and achieve $\Theta(n)$ worst case? Remarkably, yes — via a 1973 algorithm of Blum, Floyd, Pratt, Rivest, and Tarjan, often called the median-of-medians selection algorithm or simply Select. It is a triumph of theoretical computer science: the constant factor is too large for it to displace Randomized-Select in practice, but the asymptotic guarantee is unimprovable.

The high-level idea

The randomized algorithm fails when the pivot is too extreme. We need a deterministic way to guarantee a pivot that splits off at least a constant fraction of the array. Picking the actual median would do, but that's circular — computing the median is what we're trying to do.

Here is the clever workaround. An approximate median is good enough — we showed that any constant-fraction split gives linear time. So we compute an approximate median by:

  1. Group the input into chunks of $5$.
  2. Find the median of each chunk — trivial, since chunk size is constant.
  3. Recursively find the median of those medians.
Use that as the pivot. We will show it must lie in the middle 70% of the array, which is plenty.

The recursion is unusual: we recurse twice, on subproblems of sizes $n/5$ and $7n/10$. Since $1/5 + 7/10 = 9/10 < 1$, the subproblem sizes don't fill the whole array, and $T(n)$ stays linear.

Select($A$, $i$)
1 if $A$.length $\le 5$ 2 sort $A$ and return $A[i]$ 3 divide $A$ into $\lceil n/5 \rceil$ groups of $5$ (last group may be smaller) 4 for each group: find its median by sorting // $O(1)$ per group 5 let $M$ = list of group medians 6 $x$ = Select($M$, $\lceil |M|/2 \rceil$) // median of medians, recursively 7 partition $A$ around $x$; let $k$ = rank of $x$ in $A$ 8 if $i == k$ return $x$ 9 elseif $i < k$ return Select($A_{10 else return Select($A_{>x}$, $i - k$)

The Pivot is Good — The Geometric Argument

Why 5? And why does the median of medians have rank $\ge 3n/10$?

Lay out the $n/5$ groups as columns of $5$, and within each column sort the elements top-to-bottom (smallest at the top). The median of each column is the middle element — the third row down. Then sort the columns themselves by their median values, left to right. So the picture is roughly:

Look at the top-left "quadrant": columns to the left of $x$'s column, plus the top three rows of $x$'s column. Each element there is $\le$ the median of its column (top three rows) and that column's median is $\le x$ (left of $x$'s column). So all those elements are $\le x$.

How many elements is that? Roughly half the columns ($n/10$ columns) times $3$ rows $= 3n/10$. So at least $3n/10$ elements are $\le x$. Symmetrically, at least $3n/10$ are $\ge x$. Therefore $x$ has rank between $3n/10$ and $7n/10$ — squarely in the middle.

This means partitioning around $x$ produces two sides of size at most $7n/10$. Why $5$ specifically? It's the smallest odd number $g$ for which $\frac{1}{g} + 1 - \frac{3}{2g}\cdot\frac{1}{2}$ < $1$ — or, in terms of the recurrence, the smallest $g$ that makes the algorithm linear. Group size $3$ doesn't work; group size $7$ works but worse constants.

Lemma 9.5 (Pivot quality)
Let $x$ be the median-of-medians chosen on line 6. Then at least $\lceil n/4 \rceil$ elements of $A$ are $\ge x$, and at least $\lceil n/4 \rceil$ are $\le x$. (CLRS gives the slightly tighter bound $3n/10 - 6$.)
Proof of Lemma 9.5

Group $A$ into $\lceil n/5 \rceil$ groups of $5$ (the last possibly smaller). Within each group, sort the elements; identify the median. Then by definition of $x$, exactly half of the group medians are $\le x$ and half are $\ge x$ — that is, $\lceil \lceil n/5 \rceil / 2 \rceil \ge n/10$ groups have a median $\ge x$.

For each such group, the median $\ge x$ implies that the median itself plus the two larger elements of the group (the ones above the median) are all $\ge x$ — that's $3$ elements per such group. Total: $3 \cdot \lceil n/10 \rceil \ge 3n/10$ elements are $\ge x$. (Subtracting at most a constant for boundary groups, $\ge 3n/10 - 6 \ge n/4$ for $n$ large enough.) The argument for $\le x$ is symmetric. $\blacksquare$

Solving the Recurrence

Theorem 9.6 (Worst-case linear-time selection)
Select runs in $O(n)$ worst-case time.
Proof

Steps 1–5 and step 7 are $O(n)$: dividing into groups and sorting groups of size $5$ each take $O(1)$ per group times $n/5$ groups, hence $O(n)$ total; partitioning is $O(n)$ from §7.1.

Step 6 recurses on $\lceil n/5 \rceil$ elements: cost $T(n/5)$ (writing $n/5$ for $\lceil n/5 \rceil$ throughout).

Steps 9–10 recurse on a subarray of size at most $7n/10$ (by Lemma 9.5).

Adding it all up: $$T(n) \le T(n/5) + T(7n/10) + O(n).$$

Substitution. Guess $T(n) \le cn$. Then $$T(n) \le c \cdot n/5 + c \cdot 7n/10 + an = cn(1/5 + 7/10) + an = cn \cdot 9/10 + an.$$ We need $cn \cdot 9/10 + an \le cn$, i.e. $an \le cn/10$, i.e. $c \ge 10a$. Choosing $c = 10a$ closes the induction. So $T(n) = O(n)$. $\blacksquare$

Why $1/5 + 7/10 < 1$ is the only thing that matters

The recurrence $T(n) = T(\alpha n) + T(\beta n) + O(n)$ has solution $T(n) = \Theta(n)$ if and only if $\alpha + \beta < 1$. The reason: the recursion tree has total work bounded by $n + (\alpha + \beta) n + (\alpha + \beta)^2 n + \cdots$, a geometric series with ratio $\alpha + \beta$. If the ratio is $< 1$ the series sums to a constant times $n$.

For median-of-medians, $\alpha = 1/5$ (find median of medians) and $\beta = 7/10$ (recurse on partitioned side). Sum: $9/10 < 1$. Slack of $1/10$. If we used groups of $3$ instead, the bound would be $\alpha = 1/3$, $\beta = 2/3$, sum $= 1$ — the recurrence becomes $T(n) = \Theta(n \lg n)$, no longer linear. That is the magic of $5$.

Hash Tables

A dictionary supports three operations on a set of elements: Insert, Search, and Delete — each parameterized by a key. We have already seen $\Theta(\lg n)$ dictionary implementations via balanced trees; this chapter exhibits one that achieves $\Theta(1)$ expected time per operation. The trick is to convert keys into array indices using a hash function, then resolve the unavoidable collisions cleanly. Hash tables are the workhorse of practical computer science — symbol tables, caches, set membership tests, deduplication, language runtimes — and the mathematics behind them is unusually beautiful.

11.1Direct-Address Tables

When the universe $U$ of possible keys is small, the cleanest dictionary is a flat array indexed by key. To represent a set $S \subseteq U$, allocate an array $T[0\mathinner{.\,.}|U|-1]$, with $T[k]$ pointing to the element whose key is $k$ — or NIL if no such element is present.

Direct-Address-Search($T$, $k$)
1 return $T[k]$
Direct-Address-Insert($T$, $x$)
1 $T[x.\text{key}]$ = $x$
Direct-Address-Delete($T$, $x$)
1 $T[x.\text{key}]$ = NIL

Each runs in $O(1)$ worst case. The cost is space: we use $\Theta(|U|)$ memory regardless of $|S|$.

When it works, when it doesn't
Direct addressing is perfect for keys drawn from a small range — lookups into a $256$-entry array indexed by an ASCII byte, or a per-month rotation indexed by $\{1, \ldots, 12\}$. It collapses spectacularly when $|U|$ is large relative to $|S|$. A 64-bit integer key would demand $2^{64}$ slots — vastly more memory than exists. The next section is the workaround.

11.2Hash Tables & Collision Resolution by Chaining

A hash table uses an array of size $m$ much smaller than $|U|$, and squashes the universe of keys into table indices via a hash function $$h: U \to \{0, 1, \ldots, m - 1\}.$$ An element with key $k$ lives in slot $h(k)$. Since $|U| \gg m$, multiple keys may collide on the same slot. The simplest resolution is chaining: each slot holds a linked list of all elements that hashed there.

Two parameters, one tradeoff

A hash table is governed by two numbers: $m$ (slots) and $n$ (elements stored). Their ratio is the load factor $$\alpha = n / m.$$ If $\alpha$ is small, chains are short and lookups are fast — at the cost of unused slots. If $\alpha$ is large, slots are well-utilized but chains grow and lookups slow down. Resizing when $\alpha$ exceeds some threshold (typical: $1$ or $3/4$) keeps the table at a constant load factor; amortized analysis shows each insertion is still $O(1)$ on average.

The other parameter is the hash function itself. It is what determines whether elements are sprinkled evenly across slots or clump pathologically into a few. We treat it abstractly here — "uniform hashing" — and pin down good concrete choices in §11.3.

Chained-Hash-Insert($T$, $x$)
1 insert $x$ at the head of list $T[h(x.\text{key})]$
Chained-Hash-Search($T$, $k$)
1 search for an element with key $k$ in list $T[h(k)]$
Chained-Hash-Delete($T$, $x$)
1 remove $x$ from list $T[h(x.\text{key})]$

Analysis Under Simple Uniform Hashing

Simple uniform hashing
We assume any given element is equally likely to hash into any of the $m$ slots, independently of where any other element has hashed. (This is an idealization — a real $h$ is deterministic. Treat it as a model whose predictions match practice when $h$ is good.)
Theorem 11.1 (Expected search time)
In a hash table with chaining, under simple uniform hashing, an unsuccessful search takes expected time $\Theta(1 + \alpha)$. A successful search takes the same expected time.
Proof (unsuccessful search)

Computing $h(k)$ takes $O(1)$. The search then scans the entire list $T[h(k)]$ — an unsuccessful search examines every element of the chain. Under simple uniform hashing, the expected length of the chain at slot $h(k)$ is $\operatorname{E}[\text{length}(T[h(k)])] = n/m = \alpha$. Total expected time: $O(1 + \alpha)$. $\blacksquare$

What "$\Theta(1)$ expected" really requires
$\Theta(1 + \alpha)$ is $\Theta(1)$ exactly when $\alpha = O(1)$ — equivalently, $m = \Omega(n)$. So "$O(1)$ hash-table lookup" is a guarantee only as long as you keep the table from getting too full. Most real implementations double $m$ when $\alpha$ exceeds a fixed threshold; the amortized analysis (cf.\ dynamic arrays) makes the cost of resizing disappear into the per-insertion cost.

11.3Hash Functions

A good hash function spreads keys uniformly across $\{0, 1, \ldots, m-1\}$ — ideally independent of any patterns in the input. CLRS surveys three canonical constructions.

The Division Method

Division method
$$h(k) = k \bmod m.$$ Choose $m$ to be a prime not too close to a power of $2$.
Why avoid $m = 2^p$?
If $m = 2^p$, then $k \bmod m$ is just the low $p$ bits of $k$. If your keys are URLs that all end with .html, or memory addresses that are 8-byte aligned, the low bits don't carry information — collisions explode. A prime $m$ that isn't near $2^p$ mixes the bits.

The Multiplication Method

Multiplication method
Pick a constant $A \in (0, 1)$. Then $$h(k) = \lfloor m \cdot (kA \bmod 1) \rfloor,$$ where "$kA \bmod 1$" is the fractional part of $kA$.

The advantage: $m$ no longer needs to be prime — choosing $m = 2^p$ makes the implementation a quick shift-and-mask. Knuth recommends $A \approx (\sqrt{5} - 1)/2 \approx 0.618$ (the golden ratio's reciprocal), which produces excellent dispersion across a wide range of key distributions.

Universal Hashing

No fixed hash function defeats every adversary: for any deterministic $h$, an adversary aware of $h$ can choose keys all mapping to one slot. The fix is to randomize — pick $h$ uniformly at random from a carefully designed family $\mathcal{H}$ of hash functions.

Universal hash family
A finite collection $\mathcal{H}$ of hash functions from $U$ to $\{0, \ldots, m-1\}$ is universal if for every pair of distinct keys $k, \ell \in U$, $$\Pr_{h \in \mathcal{H}}[h(k) = h(\ell)] \le \frac{1}{m}.$$
Theorem 11.3 (Expected chain length under universal hashing)
Using a hash function chosen uniformly at random from a universal family, the expected number of collisions involving any particular key $k$ is at most $\alpha = n / m$, regardless of what the keys are.
The headline guarantee
Universal hashing makes the $\Theta(1 + \alpha)$ expected bound distribution-free — the expectation is taken over our random choice of $h$, not over any assumption about the keys. An adversary who sees the keys cannot construct a bad input because they cannot predict which $h$ we will use.

11.4Open Addressing

An alternative to chaining: store all elements in the table itself, with no auxiliary lists. When a slot is occupied, probe a sequence of alternative slots until an empty one is found. This is called open addressing.

Chaining vs.\ open addressing

Chaining is simple and forgiving — you can keep inserting forever, chains just grow. Open addressing has tighter memory (no pointers, single contiguous array), great cache behavior, but a strict $\alpha \le 1$ requirement: when the table is full there's nowhere to put the next element. Most modern hash table implementations (Python, Java, Go runtime maps) use open addressing for the cache advantage.

Each key $k$ defines a probe sequence $h(k, 0), h(k, 1), \ldots, h(k, m-1)$ — a permutation of $\{0, \ldots, m-1\}$ indicating slots to inspect in order. Insertion walks the sequence until it finds an empty slot; search walks it until it finds the key or an empty slot (which signals "not present").

Hash-Insert($T$, $k$)
1 $i = 0$ 2 repeat 3 $j = h(k, i)$ 4 if $T[j] == $ NIL 5 $T[j] = k$; return $j$ 6 else $i = i + 1$ 7 until $i == m$ 8 error "hash table overflow"

Probe Strategies

Three common probe sequences
Let $h'(k)$ be an auxiliary "pre-hash" function. Then:
  • Linear probing: $h(k, i) = (h'(k) + i) \bmod m$. Easy to implement; suffers from primary clustering — long runs of occupied slots grow longer.
  • Quadratic probing: $h(k, i) = (h'(k) + c_1 i + c_2 i^2) \bmod m$ for constants $c_1, c_2$. Avoids primary clustering but exhibits secondary clustering: keys with the same $h'(k)$ have identical probe sequences.
  • Double hashing: $h(k, i) = (h_1(k) + i \cdot h_2(k)) \bmod m$. Closest to uniform hashing in practice; the probe step depends on the key, so two keys agreeing in $h_1$ but not $h_2$ still get distinct sequences.
Theorem 11.6 (Expected probes, uniform hashing)
Under the idealization of uniform hashing — every probe sequence is equally likely to be any of the $m!$ permutations — with load factor $\alpha < 1$, the expected number of probes in an unsuccessful search is at most $$\frac{1}{1 - \alpha}.$$
The cliff at $\alpha = 1$
$1/(1-\alpha)$ grows mildly through $\alpha = 1/2$ (avg 2 probes) and $\alpha = 3/4$ (avg 4 probes), but explodes as $\alpha \to 1$ ($\alpha = 0.9 \Rightarrow$ 10 probes, $\alpha = 0.99 \Rightarrow$ 100). This is why open-addressing tables resize earlier than chaining tables — typically when $\alpha$ exceeds $0.5$ to $0.75$.

Chapter 16

Greedy Algorithms

A greedy algorithm commits to the locally best choice at each step, hoping the resulting sequence of local choices is globally optimal. Sometimes it is — and when it is, the algorithm is usually simple, fast, and beautiful. Sometimes it isn't, and the same approach silently produces a wrong answer. This chapter teaches you how to tell which case you are in: the two ingredients that license the greedy approach (greedy choice property and optimal substructure), and a worked contrast where the same problem is greedy-friendly in one form but greedy-toxic in another (knapsack).

16.1The Activity-Selection Problem

Activity selection
Input. A set $S = \{a_1, a_2, \ldots, a_n\}$ of activities, each with a start time $s_i$ and finish time $f_i$ ($s_i < f_i$). Two activities $a_i$ and $a_j$ are compatible if their intervals $[s_i, f_i)$ and $[s_j, f_j)$ do not overlap — that is, $f_i \le s_j$ or $f_j \le s_i$.
Output. A maximum-size subset of mutually compatible activities.
The greedy heuristic that works

Suppose activities are sorted by finish time, so $f_1 \le f_2 \le \cdots \le f_n$. The greedy rule:

Always pick the compatible activity that finishes earliest.

Why earliest finish? Picking an activity that ends sooner leaves the most remaining time for the rest. Other natural heuristics — pick the shortest activity, pick the earliest start, pick the one with fewest conflicts — all fail on some inputs. The "earliest finish" rule is the one that admits a proof.

Greedy-Activity-Selector($s$, $f$)
1 $n = s$.length 2 $A = \{a_1\}$ // $a_1$ has the earliest finish time 3 $k = 1$ 4 for $m = 2$ to $n$ 5 if $s[m] \ge f[k]$ 6 $A = A \cup \{a_m\}$ 7 $k = m$ 8 return $A$

The algorithm assumes activities are already sorted by $f_i$. If not, sort first: $O(n \lg n)$. The greedy sweep itself is $\Theta(n)$. So $\Theta(n \lg n)$ total, or $\Theta(n)$ if input is presorted.

Why the Greedy Choice Is Safe

Theorem 16.1 (Greedy choice property for activity selection)
Consider any non-empty subproblem $S_k$ — the set of activities starting at or after time $f_k$, the finish time of the most recently selected activity. Let $a_m$ be an activity in $S_k$ with the earliest finish time. Then $a_m$ is included in some maximum-size subset of mutually compatible activities of $S_k$.
Proof

Let $A_k$ be a maximum-size compatible subset of $S_k$, and let $a_j$ be its earliest-finishing activity. We exhibit a maximum-size subset that contains $a_m$.

If $a_j = a_m$, we are done. Otherwise, replace $a_j$ with $a_m$ in $A_k$ to form $A'_k = (A_k \setminus \{a_j\}) \cup \{a_m\}$.

$|A'_k| = |A_k|$, so $A'_k$ is also maximum-size. And $A'_k$ is still compatible: $a_m$ finishes no later than $a_j$ (because $a_m$ is the earliest-finishing in $S_k$), so any activity in $A_k$ that came after $a_j$ also comes after $a_m$, preserving non-overlap. $\blacksquare$

The "exchange" argument, in one sentence
Take any optimal solution that doesn't contain the greedy choice; swap in the greedy choice; show the swap doesn't hurt. This is the canonical proof technique for greedy algorithms — every greedy correctness proof in the book is some variation of it.

16.2Elements of the Greedy Strategy

When is greedy the right tool? CLRS isolates two structural properties a problem must have for greedy to succeed.

Greedy-choice property
A globally optimal solution can be reached by making a locally optimal (greedy) choice at each step. The greedy step never forces us into a position where the remaining subproblem cannot be solved optimally.
Optimal substructure
An optimal solution to the problem contains within it optimal solutions to subproblems. This is the same property that licenses dynamic programming; greedy is essentially DP where we can prove the "optimal first choice" is determined by a simple local rule — eliminating the need to try all options.
Greedy is DP with a shortcut

Every greedy algorithm could be reframed as dynamic programming. The DP would try every possible first choice, recursively solve each subproblem, and keep the best total. Greedy says: "I don't need to try every first choice — I can prove that a particular first choice is in some optimal solution, so I'll commit to it and recurse only on the resulting subproblem."

The greedy-choice property is precisely that proof. Without it, you may need to explore alternative first choices — and you are doing dynamic programming, not greedy.

The Tempting Trap — When Greedy Fails

Coin change — the same algorithm, two answers

Make change for $30\cent$ with U.S.\ coin denominations $\{25, 10, 5, 1\}$. Greedy (take the largest first): $25 + 5 = 30$. Two coins. Optimal.

Now make change for $30\cent$ with denominations $\{25, 20, 10, 5, 1\}$. Greedy: $25 + 5 = 30$, two coins. Optimal: $20 + 10 = 30$ — also two coins. Lucky.

Now make change for $40\cent$ with denominations $\{25, 20, 10, 5, 1\}$. Greedy: $25 + 10 + 5 = 40$, three coins. Optimal: $20 + 20 = 40$, two coins. Greedy fails.

The same algorithm produces a different competitive ratio depending on the denomination set. U.S.\ coins satisfy a structural property (each denomination is a "multiple-of" predecessor with enough slack) that makes greedy optimal; arbitrary denominations do not. The algorithm doesn't know which case it's in — the burden is on the analyst to prove the greedy choice property holds.

16.3Fractional vs.\ 0-1 Knapsack

Two superficially identical problems — one yields to greedy in $\Theta(n \lg n)$, the other does not yield to any known polynomial-time exact algorithm. The contrast is the cleanest illustration of the greedy-choice property in the book.

The two knapsack variants

Common setup. A thief has a knapsack of capacity $W$ pounds. There are $n$ items; item $i$ has weight $w_i$ and value $v_i$. The thief wants to maximize total value subject to the weight bound.

0-1 knapsack. Each item must be taken whole or left behind. (Integer indivisible — a gold bar.)

Fractional knapsack. Items may be taken in fractional amounts. (Divisible — gold dust, or grain.)

Why divisibility changes everything

For both problems, the natural greedy rule is: take items in decreasing order of value-per-weight, $v_i / w_i$.

In the fractional case, this is provably optimal. You fill the knapsack with the highest-density items first; when the next item won't fit, you take a fractional slice that exactly fills the remaining capacity. No room is ever wasted, and no element ever displaces a better one.

In the 0-1 case, this strategy can leave the knapsack with unused capacity that could have been filled by a lower-density item that you skipped. The greedy choice is no longer safe: committing to the highest-density item may force you to leave the knapsack underfilled in a way that a smarter strategy could avoid.

Fractional Knapsack — Greedy Works

Fractional-Knapsack($W$, items)
1 sort items by $v_i / w_i$ in decreasing order 2 $\textit{total} = 0$; $\textit{remaining} = W$ 3 for each item $i$ in sorted order 4 if $w_i \le \textit{remaining}$ 5 take all of item $i$; $\textit{total} \mathrel{+}= v_i$; $\textit{remaining} \mathrel{-}= w_i$ 6 else 7 take $\textit{remaining}/w_i$ fraction of item $i$; $\textit{total} \mathrel{+}= v_i \cdot \textit{remaining}/w_i$ 8 return $\textit{total}$ 9 return $\textit{total}$
Theorem 16.2 (Optimality for fractional knapsack)
The greedy algorithm above produces an optimal solution to the fractional knapsack problem.
Proof sketch (exchange argument)

Suppose an optimal solution $O$ uses an amount of item $j$ when there is a higher-density item $i$ with $v_i/w_i \ge v_j/w_j$ that could replace some portion of $j$. Swap a small slice: remove $\epsilon$ pounds of item $j$ (losing $\epsilon \cdot v_j/w_j$ value) and add $\epsilon$ pounds of item $i$ (gaining $\epsilon \cdot v_i/w_i$ value). Net change $\ge 0$. Repeat until $O$ matches the greedy ordering. $\blacksquare$

0-1 Knapsack — Greedy Fails

A four-line counterexample

Capacity $W = 50$. Three items:

Greedy by density: Take item 1 (weight 10, value 60), then item 2 (weight 20, value 100). Remaining capacity = 20, but item 3 weighs 30 — doesn't fit, and we cannot split it. Total value: $\mathbf{160}$.

The greedy algorithm picked the highest-density item and was permanently stuck with an unfillable $20$-pound hole. Greedy fails — not because the heuristic is silly, but because the greedy-choice property does not hold for the 0-1 variant.

Same data, different answer in fractional
Under the fractional rule on the same items: take all of item 1 (10 lb, 60), then all of item 2 (20 lb, 100), then $20/30$ of item 3 ($\frac{20}{30} \cdot 120 = 80$). Total $= 240 > 220$. The freedom to take a fraction lets greedy fill the hole.

The Fix — Dynamic Programming for 0-1 Knapsack

Because the greedy-choice property fails, 0-1 knapsack requires dynamic programming. Let $K(i, w)$ be the maximum value achievable using a subset of items $1, \ldots, i$ with total weight at most $w$. The recurrence:

$$K(i, w) = \begin{cases} 0 & \text{if } i = 0 \text{ or } w = 0, \\ K(i - 1, w) & \text{if } w_i > w, \\ \max\bigl(K(i - 1, w),\ v_i + K(i - 1, w - w_i)\bigr) & \text{otherwise.} \end{cases}$$

The table has $\Theta(nW)$ entries, each filled in $O(1)$, giving total time $\Theta(nW)$. This is pseudopolynomial: polynomial in the numeric values of the input, but exponential in the number of bits used to encode $W$. 0-1 knapsack is in fact NP-hard; no polynomial-time exact algorithm is known.

The deep moral
Two problems that look identical except for one word ("fractional" vs.\ "whole") have wildly different complexity profiles — one is $O(n \lg n)$ greedy, the other is NP-hard. The shape of the optimization landscape — whether the greedy-choice property holds — matters enormously, and small-seeming modeling decisions can change it.

Single-Source Shortest Paths

Given a weighted directed graph $G = (V, E)$ with edge weights $w: E \to \mathbb{R}$ and a designated source $s \in V$, the single-source shortest-paths problem asks: for every vertex $v \in V$, find the minimum-weight path from $s$ to $v$. This chapter develops two cornerstone algorithms — Bellman–Ford (handles negative edges, $O(VE)$) and Dijkstra (forbids negative edges but runs in $O((V + E) \lg V)$). Both rest on the same underlying primitive: relaxation.

24.0Foundations & Relaxation

Shortest-path weight
The weight of a path $p = \langle v_0, v_1, \ldots, v_k \rangle$ is $w(p) = \sum_{i=1}^{k} w(v_{i-1}, v_i)$. The shortest-path weight from $u$ to $v$ is $$\delta(u, v) = \begin{cases} \min\{ w(p) : p \text{ is a path from } u \text{ to } v \} & \text{if such a path exists,} \\ \infty & \text{otherwise.} \end{cases}$$ If a negative-weight cycle is reachable from $u$ on the way to $v$, we set $\delta(u, v) = -\infty$.
Why we care about negative cycles
Negative-weight cycles break shortest paths entirely. If you can loop through a cycle with negative total weight, you can keep looping to drive the path weight to $-\infty$. So either we forbid such cycles in the input, or our algorithm must detect them — which is one of Bellman–Ford's headline features.

Algorithm Skeleton — Estimates and Predecessors

Both algorithms maintain two arrays:

  • $d[v]$ — the current shortest-path estimate: an upper bound on $\delta(s, v)$.
  • $\pi[v]$ — the predecessor of $v$ in the current shortest-path tree (or NIL if none yet).
Initialize-Single-Source($G$, $s$)
1 for each vertex $v \in G.V$ 2 $v.d = \infty$ 3 $v.\pi = $ NIL 4 $s.d = 0$

Relaxation — the Atomic Step

Relax
Given an edge $(u, v)$ with weight $w(u, v)$, the operation Relax($u, v, w$) asks: can the estimate at $v$ be improved by going through $u$?
Relax($u$, $v$, $w$)
1 if $v.d > u.d + w(u, v)$ 2 $v.d = u.d + w(u, v)$ 3 $v.\pi = u$
Relaxation is the only operation

Every shortest-path algorithm in this chapter is some pattern of relaxations. Bellman–Ford relaxes every edge $|V| - 1$ times. Dijkstra relaxes the edges out of one carefully-chosen vertex at a time. They differ in which relaxations they perform and in what order, not in what they do.

The invariant maintained throughout is: $d[v] \ge \delta(s, v)$ always, with equality once the algorithm has done enough work.

Lemma 24.10 (Convergence)
If $s \rightsquigarrow u \to v$ is a shortest path in $G$, and if $u.d = \delta(s, u)$ at some point before a call to Relax$(u, v, w)$, then $v.d = \delta(s, v)$ at all times afterward.
Proof
After the relax, $v.d \le u.d + w(u, v) = \delta(s, u) + w(u, v) = \delta(s, v)$ (using optimal substructure of shortest paths: a subpath of a shortest path is itself shortest). Combined with the invariant $v.d \ge \delta(s, v)$, we conclude $v.d = \delta(s, v)$. $\blacksquare$

24.1The Bellman–Ford Algorithm

Bellman–Ford solves the single-source shortest-paths problem on graphs that may contain negative-weight edges (but no negative cycles reachable from the source). It also detects the presence of a reachable negative cycle, returning False if one exists.

The simple idea

A shortest path in a graph with $|V|$ vertices uses at most $|V| - 1$ edges (any longer path repeats a vertex, hence contains a cycle, which we could excise without increasing weight unless the cycle is negative — the case we forbid).

So if we relax every edge of the graph $|V| - 1$ times, after pass $k$ all estimates corresponding to shortest paths using $\le k$ edges are exact. After $|V| - 1$ passes, all shortest-path estimates are exact.

The detection bonus: do one more pass. If any edge can still be relaxed, there must be a path of length $\ge |V|$ that improves on a path of length $|V| - 1$ — only possible if the graph contains a reachable negative cycle.

Bellman-Ford($G$, $w$, $s$)
1 Initialize-Single-Source($G$, $s$) 2 for $i = 1$ to $|G.V| - 1$ 3 for each edge $(u, v) \in G.E$ 4 Relax($u$, $v$, $w$) 5 for each edge $(u, v) \in G.E$ 6 if $v.d > u.d + w(u, v)$ 7 return False // negative cycle detected 8 return True

The two nested loops on lines 2–4 run $\Theta((|V| - 1) \cdot |E|) = \Theta(VE)$ times. The cycle-check pass on lines 5–7 adds $\Theta(E)$. Total: $\Theta(VE)$.

Theorem 24.4 (Correctness of Bellman–Ford)
Let $G = (V, E)$ be a weighted directed graph with source $s$ and weight function $w$. If $G$ contains no negative-weight cycles reachable from $s$, then after Bellman-Ford terminates, $v.d = \delta(s, v)$ for all $v$ reachable from $s$, and it returns True. If $G$ does contain a negative-weight cycle reachable from $s$, Bellman-Ford returns False.
Proof sketch

By induction on $i$: after the $i$-th iteration of the outer loop, $v.d = \delta(s, v)$ for every $v$ whose shortest path from $s$ uses at most $i$ edges. The base case $i = 0$ holds: $s.d = 0 = \delta(s, s)$, and $v.d = \infty$ for $v$ unreachable in $0$ edges. The step uses Lemma 24.10 (Convergence): if $\delta(s, v)$ is achieved via predecessor $u$ on an $(i+1)$-edge path, then $u.d = \delta(s, u)$ by inductive hypothesis, and the relaxation of $(u, v)$ in iteration $i + 1$ sets $v.d = \delta(s, v)$.

Since shortest paths use at most $|V| - 1$ edges, by iteration $|V| - 1$ all $v.d$ are exact. If a negative cycle existed, no such bound holds and some edge would still relax on the $|V|$-th pass; the check on lines 5–7 catches it. $\blacksquare$

When to use it
Bellman–Ford's $\Theta(VE)$ runtime is worse than Dijkstra's $\Theta((V + E) \lg V)$, but it tolerates negative edge weights. The classic use case is currency arbitrage detection: edge $(u, v)$ has weight $-\log(\text{exchange rate from } u \text{ to } v)$, and a negative cycle means a sequence of trades that multiplies your money — an arbitrage opportunity.

24.3Dijkstra's Algorithm

Dijkstra's algorithm solves single-source shortest paths in $O((V + E) \lg V)$ time using a binary min-heap (or $O(E + V \lg V)$ with a Fibonacci heap), provided all edge weights are nonnegative. It is a greedy algorithm: at each step it commits to the vertex whose tentative distance is smallest, never to be revisited.

Why nonneg, and why greedy

The algorithm maintains a set $S$ of "settled" vertices — ones whose shortest-path estimate is known to be exact. Repeatedly, it pulls the unsettled vertex $u$ with the smallest $d[u]$ and adds it to $S$, then relaxes all edges out of $u$.

The greedy choice works because of nonnegative weights: once $d[u]$ is the smallest among unsettled vertices, no longer path through some other unsettled vertex can ever be shorter (it would have to traverse one or more nonneg edges to even reach $u$, making it $\ge d[u]$). With negative edges, this argument collapses — a longer-looking path might be made shorter by a future negative edge — which is why Dijkstra requires nonnegativity.

Correctness

Theorem 24.6 (Correctness of Dijkstra)
Run on a weighted directed graph $G = (V, E)$ with nonneg weights and source $s$, Dijkstra terminates with $u.d = \delta(s, u)$ for all $u \in V$.
Proof (loop invariant: every extracted $u$ has $u.d = \delta(s, u)$)

By induction on the extraction order. Suppose for contradiction $u$ is the first vertex extracted with $u.d \ne \delta(s, u)$. Then $u \ne s$ (since $s.d = 0 = \delta(s, s)$), so there exists a shortest path $s \rightsquigarrow u$. Let $y$ be the first vertex on this path not in $S$ at the moment $u$ is extracted, and let $x$ be its predecessor on the path (so $x \in S$).

By induction $x.d = \delta(s, x)$. When $x$ was added to $S$, we relaxed $(x, y)$, so $y.d \le x.d + w(x, y) = \delta(s, y)$. Hence $y.d = \delta(s, y) \le \delta(s, u) \le u.d$. But Dijkstra picked $u$, not $y$ — meaning $u.d \le y.d$. Combined: $u.d \le y.d \le \delta(s, u) \le u.d$, so $u.d = \delta(s, u)$. Contradiction. $\blacksquare$

Where nonnegativity sneaks in
The step $\delta(s, y) \le \delta(s, u)$ uses that the path from $s$ to $u$ continues from $y$ via nonnegative edges. With negative edges, $\delta(s, u)$ could be smaller than $\delta(s, y)$, breaking the proof. (Try Dijkstra on a graph with a negative edge: it can lock in an estimate too early and never revise.)

Chapter 25

All-Pairs Shortest Paths

The single-source problem of Chapter 24 finds the shortest paths from one designated source to every other vertex. The all-pairs problem asks for $\delta(u, v)$ for every pair $(u, v) \in V \times V$. One could run Dijkstra from each vertex in turn ($O(V \cdot (V + E) \lg V)$ for nonneg graphs); but the elegant alternative — Floyd–Warshall — handles negative edges (as long as no negative cycle exists), uses only $\Theta(V^3)$ time independent of $|E|$, and is so simple it fits in about ten lines.

25.2The Floyd–Warshall Algorithm

Floyd–Warshall is a dynamic-programming algorithm. Number the vertices $1, 2, \ldots, n$. The central object is a sequence of matrices $D^{(0)}, D^{(1)}, \ldots, D^{(n)}$, where $D^{(k)}[i][j]$ is the weight of the shortest path from $i$ to $j$ whose intermediate vertices come from the set $\{1, 2, \ldots, k\}$.

The key DP move

Consider a shortest path $p$ from $i$ to $j$ using intermediate vertices in $\{1, \ldots, k\}$. There are two cases:

  1. $p$ does not use vertex $k$. Then $p$ uses only intermediates from $\{1, \ldots, k - 1\}$, so its weight is $D^{(k-1)}[i][j]$.
  2. $p$ does use vertex $k$. Then $p$ splits at $k$: the subpath $i \rightsquigarrow k$ uses intermediates in $\{1, \ldots, k - 1\}$ (vertex $k$ appears as an endpoint, not an intermediate), and similarly for $k \rightsquigarrow j$. Total weight: $D^{(k-1)}[i][k] + D^{(k-1)}[k][j]$.

The shortest path is the better of the two: $$D^{(k)}[i][j] = \min\bigl(D^{(k-1)}[i][j],\ D^{(k-1)}[i][k] + D^{(k-1)}[k][j]\bigr).$$ This is the recurrence. Everything else is bookkeeping.

Base case and recurrence
$$D^{(0)}[i][j] = \begin{cases} 0 & \text{if } i = j, \\ w(i, j) & \text{if } i \ne j \text{ and } (i, j) \in E, \\ \infty & \text{otherwise.} \end{cases}$$ For $k = 1, 2, \ldots, n$: $$D^{(k)}[i][j] = \min\bigl(D^{(k-1)}[i][j],\ D^{(k-1)}[i][k] + D^{(k-1)}[k][j]\bigr).$$ The final matrix $D^{(n)}$ contains $\delta(i, j)$ for all pairs: every vertex is now an allowed intermediate.
Floyd-Warshall($W$)
1 $n = W.\text{rows}$ 2 $D^{(0)} = W$ 3 for $k = 1$ to $n$ 4 let $D^{(k)} = (d^{(k)}_{ij})$ be a new $n \times n$ matrix 5 for $i = 1$ to $n$ 6 for $j = 1$ to $n$ 7 $d^{(k)}_{ij} = \min(d^{(k-1)}_{ij},\ d^{(k-1)}_{ik} + d^{(k-1)}_{kj})$ 8 return $D^{(n)}$
In-place implementation
Although the recurrence references $D^{(k-1)}$, in practice we can overwrite $D$ in place — using a single matrix updated through $n$ passes. Reason: when we update $D[i][j]$, the values $D[i][k]$ and $D[k][j]$ we read are correct whether we're reading the old (round $k-1$) value or the new (round $k$) value — both equal $D^{(k-1)}[i][k]$ and $D^{(k-1)}[k][j]$ respectively (proof: any shortest path through $k$ that has $k$ as an intermediate uses $k$ exactly once, so the $D[i][k]$ subpath does not have $k$ as an intermediate). This reduces space from $\Theta(n^3)$ to $\Theta(n^2)$.
Theorem 25.5 (Floyd–Warshall correctness & complexity)
Floyd-Warshall computes $D^{(n)}[i][j] = \delta(i, j)$ for all $i, j$ on a graph with no negative-weight cycles. It runs in $\Theta(V^3)$ time and $\Theta(V^2)$ space (in place).
Proof (correctness by induction on $k$)

Base. $D^{(0)}[i][j] = w(i, j)$ for direct edges and $\infty$ otherwise — this is the shortest $(i, j)$ path using no intermediates. Correct.

Step. Assume $D^{(k-1)}[i][j]$ is the shortest-path weight using intermediates in $\{1, \ldots, k-1\}$. A shortest path using intermediates in $\{1, \ldots, k\}$ either avoids $k$ (weight $D^{(k-1)}[i][j]$) or visits $k$ (weight $D^{(k-1)}[i][k] + D^{(k-1)}[k][j]$, by optimal substructure: each subpath is shortest under the smaller intermediate set). The min of these is $D^{(k)}[i][j]$. $\blacksquare$

Time. Three nested loops, each running $n$ times, with constant-time bodies: $\Theta(n^3)$.

Floyd–Warshall on a 4-vertex graph

Consider a graph on vertices $\{1, 2, 3, 4\}$ with weighted edges: $1 \to 2\,(3)$, $1 \to 3\,(8)$, $2 \to 4\,(1)$, $3 \to 2\,(4)$, $4 \to 1\,(2)$, $4 \to 3\,(-5)$.

Reconstructing the Paths

Floyd–Warshall as stated returns only the weights. To recover the actual paths, maintain a parallel predecessor matrix $\Pi^{(k)}[i][j]$:

$$\Pi^{(k)}[i][j] = \begin{cases} \Pi^{(k-1)}[i][j] & \text{if } d^{(k-1)}_{ij} \le d^{(k-1)}_{ik} + d^{(k-1)}_{kj}, \\ \Pi^{(k-1)}[k][j] & \text{otherwise.} \end{cases}$$

$\Pi[i][j]$ is the predecessor of $j$ on the current best path from $i$. To print the path from $i$ to $j$, recurse: print the path from $i$ to $\Pi[i][j]$, then print $j$.

Q1. What does the index $k$ represent in $D^{(k)}[i][j]$?
  • The number of edges in the shortest path.
  • The number of vertices in the path.
  • The maximum index of any intermediate vertex on the shortest path from $i$ to $j$ (intermediates are restricted to the set $\{1, \ldots, k\}$).

The whole DP is parameterized by which set of vertices may serve as intermediates. Growing $k$ from $0$ to $n$ progressively unlocks more transit options, ending with $D^{(n)}$ where every vertex is allowed — the true all-pairs shortest paths.
Q2. Why is Floyd–Warshall $\Theta(V^3)$ regardless of $|E|$?
  • The triple nested loop iterates over all ordered triples $(k, i, j)$ of vertices, doing constant work each; the edges only matter in the initial matrix $D^{(0)}$.
  • Edges have constant weight.
  • The graph is assumed dense.
  • The matrix is always full.
After loading $W$ into $D^{(0)}$, the algorithm references only the matrix, never the edge list. Total operations: $n \cdot n \cdot n = n^3$.
Q3. When does it make sense to use Floyd–Warshall instead of running Dijkstra from every vertex?
  • When the graph is sparse and edges are nonnegative.
  • When $|V|$ is very large.
  • Never — Dijkstra is always faster.
  • When the graph is dense (so $|E| = \Theta(V^2)$) and/or has negative edges. Floyd–Warshall is $\Theta(V^3)$ regardless; running Dijkstra from each vertex is $\Theta(V \cdot (V + E) \lg V) = \Theta(V^3 \lg V)$ on a dense graph — worse — and Dijkstra fails entirely on negative edges.
On a dense graph $E = \Theta(V^2)$, $V$ Dijkstra runs cost $\Theta(V^3 \lg V)$, slower than $\Theta(V^3)$ Floyd–Warshall. On a sparse graph $E = \Theta(V)$, Dijkstra-from-each gives $\Theta(V^2 \lg V)$, which beats $\Theta(V^3)$ — so use Dijkstra there. Negative edges force the choice regardless.
